## Critical correction to [[fossils-migration-plan]]

The plan describes Phase 8 as auditing/cleaning up *already-ported* mixins. That premise was wrong: before this session, `src/main/resources/fossil.mixins.json` had empty `mixins`/`client` arrays and there was no `mixin` package under `src/main/java` at all. **Phase 8 is actually the first real port of the mod's own mixins**, not a trim pass. (Unrelated: `more-hitboxes`'/GeckoLib's/TerraBlender's *own* bundled mixins were already working via the jar-patch fix in [[fossils-morehitboxes-mixin-registration-fix]] - don't confuse those with this mod's own `com.github.fossil.mixin.*` classes, which are the subject of this phase.)

## Toolchain finding (Task 1) - much smaller lift than expected

No Gradle Mixin plugin or explicit `mixinextras` dependency was needed. `net.neoforged.moddev` (ModDevGradle) already pulls `sponge-mixin`+`mixinextras-neoforge` onto the classpath transitively, and `src/main/templates/META-INF/neoforge.mods.toml` already had a `[[mixins]] config="${mod_id}.mixins.json"` block (leftover scaffolding from the project template, never removed). Zero `build.gradle` changes were required - just write mixin classes and register them in `fossil.mixins.json`'s `mixins` (both-sides) / `client` arrays.

## Testing technique gotcha (learned the hard way, reusable for all future mixin/runtime testing)

`./gradlew runServer` / `runClient` **forks a detached JVM that outlives the gradle wrapper task**. The wrapper process can report exit 0 in ~1-15s while the actual game JVM keeps running in the background for the full session - or, if a previous instance is still bound to the server port, a *new* attempt's JVM dies fast on a port conflict while gradle still reports "completed". This produces very confusing "the log stopped growing / mixin never got exercised" symptoms.

**Correct pattern:**
1. `rm -f run/logs/debug.log` before each attempt.
2. Launch with `nohup ./gradlew runServer --console=plain > /tmp/x.log 2>&1 &` (background).
3. `sleep 40`ish, then verify the *actual game JVM* is alive: `ps aux | grep "net.minecraft"` (client) - look for the real classpath-heavy java process, not the gradle wrapper.
4. Check `run/logs/debug.log` for `Mixing X from fossil.mixins.json into ...` lines (success) vs `FATAL`/`InvalidInjectionException` (failure - these are loud and unambiguous, "0/1 succeeded... No refMap loaded" etc).
5. Server reaching `Done (Ns)!` is a good proxy for "got far enough to exercise most mixins," but some (e.g. entity-attached ones) only fire during actual world/entity load - a world with saved entities exercises far more than a fresh world.
6. **Stop cleanly afterward** - server: RCON `stop` (creds already in `run/server.properties`: `enable-rcon=true`, `rcon.password=claudetest`, `rcon.port=25575`; python one-liner socket script works, no `mcrcon` binary installed). Client: `pkill -f "net.neoforged.devlaunch.Main"`. Always verify via `ps aux | grep net.minecraft` that nothing lingers before starting the next attempt - stacked lingering JVMs is exactly what caused the confusing repeat-failure pattern above.

## API-drift discoveries (all confirmed via decompiled 1.21.1 source, extractable from `~/.gradle/caches/neoformruntime/intermediate_results/sourcesAndCompiledWithNeoForge_*_output.jar` - contains real `.java` sources with Mojang mappings, not obfuscated - `unzip -l <jar> | grep ClassName` to find the right jar, they change hash per build so re-glob if stale)

- **`WalkNodeEvaluator.isBurningBlock`/`getBlockPathTypeRaw` are GONE.** `isBurningBlock` moved to the parent `NodeEvaluator` class; `getBlockPathTypeRaw` was folded into a restructured static `getPathTypeFromState(BlockGetter, BlockPos)`. **Correct fix wasn't a mixin at all**: NeoForge added `IBlockExtension.getBlockPathType(BlockState, BlockGetter, BlockPos, Mob)` - a default method any `Block` subclass overrides to declare its own danger level (vanilla's own `Blocks.LAVA` uses exactly this). Target already has a real `TarBlock` subclass (`src/main/java/com/github/fossil/block/custom_blocks/TarBlock.java`) - added `getBlockPathType(...) { return PathType.LAVA; }` there instead. This fully supersedes that half of `WalkNodeEvaluatorMixin`; the mixin now only keeps the genuinely-mixin-only `findAcceptedNode`/`canReachWithoutCollision` fence-corner-stuck fix.
- **`TitleScreen` panorama rendering was restructured.** `render()` no longer calls `PanoramaRenderer.render(F,F)` directly - it calls an overridable `renderPanorama(GuiGraphics, float)` hook (which `TitleScreen` itself overrides to delegate to a `CubeMap`/`PANORAMA` field), and `renderBackground` is now an empty override (vanilla dropped the overlay-blit that the old mixin's second wrap used to suppress - nothing to suppress anymore). Fix: single `@Inject(method="renderPanorama", at=@At("HEAD"), cancellable=true)` that draws our two parallax layers and cancels (skipping vanilla's panorama) when `Config.customMainMenu` is true. Simpler than the original 3-injection version.
- **`PlayerInfo.getCapeLocation`/`getElytraLocation` are GONE entirely.** Cape/elytra textures moved into an immutable `PlayerSkin` record (`net.minecraft.client.resources.PlayerSkin`, components: `texture, textureUrl, capeTexture, elytraTexture, model, secure`) returned by `PlayerInfo.getSkin()`. Fix: `@ModifyReturnValue(method="getSkin", at=@At("RETURN"))` that returns a new `PlayerSkin` with `capeTexture`/`elytraTexture` swapped for dev/contributor UUIDs, everything else copied from the original record.
- **`Minecraft.clearLevel(Screen)` renamed to `disconnect(Screen)`.** Straight rename, same shape (`void`, one `Screen` param).
- **`LevelRenderer.renderLevel` signature dropped its `PoseStack` parameter entirely** (new sig: `DeltaTracker, boolean, Camera, GameRenderer, LightTexture, Matrix4f, Matrix4f`). The method still has a local `PoseStack posestack = new PoseStack()` created near its top and threaded through camera-relative (each draw call manually offsets by `-cameraPos`, the poseStack itself carries no persistent camera rotation). Camera view rotation is applied separately via a `Matrix4fStack`/`RenderSystem.applyModelViewMatrix()` that gets **popped near the very end of the method**, before a blind `@At("TAIL")` injection point would fire - meaning TAIL is the wrong injection point now (loses camera rotation state). Fix: capture the local `PoseStack` via mixinextras `@Local`, and retarget the injection to `@At(value="INVOKE", target=".../LevelRenderer;renderDebug(PoseStack,MultiBufferSource,Camera)V", shift=AFTER)` - the exact point vanilla itself uses for world-space debug drawing, still inside the active camera-rotation scope. Also: the mixin's `finishNanoTime` param no longer exists on the method signature at all, but tracing its actual use inside `InstructionRenderUtil`/target's render helpers showed it's only ever used as a monotonic clock for a `sin()`-based pulse animation, not a real frame deadline - safely replaced with `System.nanoTime()`.

## Miscategorization found in the original plan

`ChunkStatusMixin` was listed in [[feedback-keep-debug-tooling-mixins]] as one of "4 dev-only debug-tooling mixins" to keep. It's actually unrelated to debugging: it forces `AnuLairChunkGenerator`/`TreasureChunkGenerator` to populate structures even if a player disabled "Generate Structures" at world creation - a real gameplay necessity for the boss dimensions, not dev tooling. The "keep it" outcome is unchanged, but it belongs in the worldgen-fragile bucket (Task 8), not the debug bucket, and targets an obfuscated Yarn-intermediary method name (`method_39464`) that still needs re-resolving against 1.21.1 Mojang mappings - not yet done.

## Decisions made this session

- **`JigsawStructureMixin` (Lithostitched compat) and `PickupHandlerMixin` (CarryOn compat) deferred to Phase 9**, not ported in Phase 8. Both third-party mods DO have confirmed official NeoForge 1.21.1 builds (checked via web search 2026-08-14: Lithostitched on [CurseForge](https://www.curseforge.com/minecraft/mc-mods/lithostitched)/[Modrinth](https://modrinth.com/mod/lithostitched), CarryOn on [CurseForge](https://www.curseforge.com/minecraft/mc-mods/carry-on)) - the deferral is purely because both mixins are optional `Platform.isModLoaded(...)`-gated compat, which the migration plan's dependency policy puts in Phase 9 scope, not because of availability concerns.
