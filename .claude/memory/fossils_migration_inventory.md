Raw scale/catalog data behind [[fossils-migration-plan]]. This is a point-in-time snapshot of the SOURCE repo (`~/IdeaProjects/FossilsArcheologyRevival`) — re-verify specifics (file counts, class names) against current source before relying on them, and check the TARGET repo (`~/IdeaProjects/FossilsAndArcheologyRevival`) directly for what's actually been ported so far rather than assuming from this file.

**Why kept:** gathering this required 7 parallel research passes over ~1000+ source files; re-deriving it from scratch every session would be wasteful. **How to apply:** consult this when scoping a specific phase from [[fossils-migration-plan]] to know roughly how much source content that phase covers, then re-read the actual current source files before porting (don't trust remembered file:line specifics).

## Scale by common-module package (java file counts)

entity 199, client 109, block 76, world 42, item 35, compat 32, network 25, mixin 23, recipe 13, inventory 7, food 6, advancements 5, util 5, tags 3, sounds 3, enchantment 3, material 2, villager 2, loot 2, capabilities 1, config 1, event 1. Plus forge module (~15 block files + large compat/datagen tree) and fabric module (~9 block files + Cardinal Components/MidnightConfig-specific code, entirely droppable).

## Blocks (already scoped in detail separately)

221 `RegistrySupplier<Block>` entries in `ModBlocks.java`, 52 custom `Block` subclasses (`block/custom_blocks/`), 13 `BlockEntity` classes (`block/entity/`). 3 blocks (FossilLeaves, FlammableRotatedPillar, Tar) have forge/fabric-split "Impl" classes that fold into one NeoForge class each. Resources: 20 blockstates, 86 models, 340 textures, 251 generated loot tables, 12 tag files — datagen-driven via the Forge module's providers.

## Entities (`entity/`, 199 files)

~65 dinosaur/fish/bird/aquatic-reptile/arthropod entities, all inheriting a single monolithic base class `Prehistoric.java` (1694 lines) or its variants `PrehistoricFish`/`PrehistoricFlying`/`PrehistoricSwimming`. 6 custom monster/boss entities (`AnuBoss`, `Anubite`, `AnuDead` phase-boss with 8-file AI state machine, `Failuresaurus`, `FriendlyPiglin`, `SentryPiglin`, `TarSlime`). Misc: projectiles (`Javelin`, `ThrownBirdEgg`, `LaserPointEntity`, `AncientLightningBolt`), `StoneTablet`, `PrehistoricSkeleton` (decorative multi-hitbox display), toys (`ToyBall`, `ToyTetheredLog`, `ToyScratchingPost`), `DinosaurEgg`. ~34 custom AI goals, custom navigation/node-evaluators, modular per-entity subsystems (`AISystem`, `MoodSystem`, `SleepSystem`, `LeapSystem`, `SitSystem`) plugged into `Prehistoric` via `registerSystem()`. Data-driven stats/AI via `EntityDataLoader`/`PrehistoricEntityInfo` JSON, plus a full data-driven skin/variant engine (`entity/variant/`). Registration: standard Architectury `DeferredRegister<EntityType<?>>` in `ModEntities.java` — mechanical 1:1 port to NeoForge's own `DeferredRegister`. No custom `EntityDataSerializer`s (all vanilla serializers) — simplifies one migration axis. GeckoLib coupling is deep (see plan's risk gate #1). more-hitboxes coupling is concentrated in exactly 2 files (`Prehistoric.java`, `PrehistoricSkeleton.java`) but affects every dinosaur transitively. Capabilities backing mammal-pregnancy/first-hatch data are Forge `Capability`+mixin vs Fabric Cardinal Components — collapses to one NeoForge Data Attachment implementation.

## Client (`client/`, 109 files)

GeckoLib 4.7.2. Core pattern: one generic `PrehistoricGeoRenderer`/`PrehistoricGeoModel` pair drives ~60 entity renderers (just asset name + RenderType function per species), mirrored by `PrehistoricFishGeoRenderer`/Model for fish. Standalone GeckoLib renderers for bosses/monsters (`SkeletonRenderer`, `FailuresaurusRenderer`, `AnuBossRenderer`, etc.). Vanilla-style `RenderLayer` overlays (`AnuBossGlowLayer`), GeckoLib armor renderer (`AncientHelmetRenderer extends GeoArmorRenderer`). Block-entity renderers are plain `ModelPart`/`BlockEntityRenderer`, NOT GeckoLib (lower risk): `CultureVatRenderer`, `SarcophagusRenderer`, `AncientChestRenderer`, `AnuStatueRenderer`, `AnubiteStatueRenderer`, `AnuBarrierRenderer`. GUIs: 5 simple machine screens (Analyzer/Sifter/CultureVat/Worktable/Feeder, all low-risk `AbstractContainerScreen`s), `DinopediaScreen` (489 lines, most complex non-debug screen), large debug-only subsystem (`DebugScreen` + `PathingScreen` + 14-file pathing-visualization stack — recommend dropping, dev-only). Forge/Fabric split: custom baked-model plant system (Forge `IModelGeometry`/`IModelLoader` vs Fabric equivalent — use Forge's as the NeoForge seed), `ClientModEvents` (tar screen overlay), `CustomItemRendererFabricImpl` (drop, Forge-side already handles this).

## Items/food/material/loot/villager/enchantment/tags/advancements/sounds

`item/` 35 files, ~1656 LOC, standard Architectury `DeferredRegister<Item>` pattern in `ModItems.java`. Complexity ranges from trivial wrappers to `LaserPointerItem` (175 lines, stateful raycast). Only 3 files use raw NBT (`StoneTabletItem`, `LaserPointerItem` — best Data Component migration candidate, `ArtificialHoneycombItem` — vanilla spawn-egg-style NBT, fine to keep as `CustomData`). `food/` (6 files): custom JSON-driven food-value layer (`FoodType`/`Diet`/`FoodMappings`) on top of vanilla `FoodProperties` — needs revalidation against 1.21's `FoodProperties`/`Consumable` component split but the layer itself ports cleanly. `material/` (2 files): `ModArmorMaterials`, `ModToolTiers` (plain enums implementing `ArmorMaterial`/`Tier` — low risk), `ModFluids`/`TarFluid` (Architectury fluid attributes — needs full NeoForge-native rewrite, see plan). `loot/` (2 files): one custom function, GSON-Serializer-based (needs MapCodec rewrite). `villager/` (2 files): 2 custom professions, trade lists referencing enchantments. `enchantment/` (3 files): 2 Java `Enchantment` subclasses — full datapack-JSON rewrite needed (see plan). `tags/`/`advancements/`/`sounds/`: mostly Java constant holders + a few `SimpleCriterionTrigger` classes, actual tag/advancement trees are JSON. Per-loader split: only 6 paired `item/{forge,fabric}` classes, all GeckoLib armor-renderer client wiring (`IClientItemExtensions` vs `RenderProvider`) — collapse to one class each using the Forge (`IClientItemExtensions`) shape.

## Networking/recipes/menus/capabilities/machines

`network/` (25 files): architectury-networking `NetworkChannel` wrapper, ~19 active packets + ~11 debug-only ones, uniform hand-rolled write/read/apply/register boilerplate — mechanical but voluminous rewrite to `CustomPacketPayload`+`StreamCodec`. `recipe/` (13 files): vanilla-shaped `Recipe`/`RecipeSerializer`/`RecipeType`, two base abstractions (`MultiOutputAndSlotsRecipe` for Analyzer/Sifter, `WithFuelRecipe` for CultureVat/Worktable) — low risk, ports near-unchanged. `inventory/` (7 files): plain `AbstractContainerMenu` subclasses, low risk. `capabilities/` (1 file, `ModCapabilities`): `@ExpectPlatform` façade over (a) mammal pregnancy/embryo data, (b) player first-hatch flag, (c) `CommonEnergyStorage` (loader-agnostic energy interface) — Forge backing uses real `Capability<T>`+`LazyOptional`, Fabric uses Cardinal Components + Team Reborn Energy (a genuinely different transactional energy model, drop entirely). Forge exposes item-handler/energy to hoppers via 2 mixins (`EnergyContainerBlockEntityMixin`, `MachineContainerBlockEntityMixin`) — Fabric has no equivalent (automation may have been Forge-only already). Machine block entities (one-liners): `AnalyzerBlockEntity` (bones/eggs→DNA, energy-consuming), `SifterBlockEntity` (sediment→fossils, no power), `CultureVatBlockEntity` (fuel+energy dual-consuming crafting), `WorktableBlockEntity` (fuel-only furnace-style crafting), `EnergyContainerBlockEntity`/`MachineContainerBlockEntity` (abstract bases), `FeederBlockEntity` (feeds nearby dinosaurs per Diet), `AncientChestBlockEntity` (one-shot lid-animation loot chest), `BubbleBlowerBlockEntity` (pure mood-system toy trigger, no inventory/energy).

## Compat/mixins/config

`compat/` (32 common files): JEI (heavy, full `IModPlugin`, 4 recipe types), EMI (heavy, near-duplicate of JEI), REI (heaviest, split client/server plugins), Farmer's Delight (light, common), GeckoLib override/patch classes (medium, coupled to mixins). Forge/fabric-only compat trees (much larger, all droppable/deferrable): Farmer's Delight addons (22 Forge classes vs 13 Fabric — per-mod delight integrations like AlexsMobs/ArsNouveau/BYG/etc.), Jade (3 providers × 2 loaders), Alex's Mobs (Forge-only). `mixin/` (23 common + 5 forge + 6 fabric-drop): categorized in the plan's architecture-decisions section by whether NeoForge/1.21.1 makes them unnecessary. `config/` (1 file, `FossilConfig`): `@ExpectPlatform` over Forge `ForgeConfigSpec` (port target) vs Fabric MidnightConfig (drop, plus its 2 dedicated mixins).

## World generation (`world/`, 42 files)

3 biomes (`anu_lair`, `treasure_room`, `volcano` — only `volcano` is an overworld replacement, via TerraBlender), 2 custom dimensions sharing one hardcoded `DimensionType`, 3 custom `ChunkGenerator` subclasses with real generation logic (no density functions — `SingleStructureChunkGenerator` base → `AnuLairChunkGenerator`, `TreasureChunkGenerator`), 3 custom `Structure` subclasses (`AnuCastleStructure`, `HellBoatStructure`, `TreasureRoomStructure`) plus jigsaw/template-pool structures (aztec temple, fossil sites, tar sites — JSON-driven, lower risk), 17 configured/14 placed features including custom `Feature` classes for volcano decoration, 6 custom tree types (feature + `AbstractTreeGrower` pairs, used by `ModBlocks`' log/wood registration), one custom surface rule for volcano terrain. TerraBlender used only for the volcano biome swap (see plan's risk gate #3). Forge uses datapack-driven `BiomeModifier`s (direct NeoForge port target); Fabric uses imperative `BiomeModifications` calls with runtime config-gating (that dynamism, if wanted, needs folding into the NeoForge bootstrap differently since biome modifiers bake once at datapack load).

## Build/loader architecture

Source toolchain: Java 17, `architectury-plugin` 3.4-SNAPSHOT, `dev.architectury.loom` 1.10-SNAPSHOT, MC 1.20.1, Forge 47.4.3, Fabric API 0.92.6/loader 0.16.7, architectury 9.2.14. Hard deps needing a NeoForge 1.21.1 build check: GeckoLib 4.7.2, TerraBlender 3.0.1.10, more-hitboxes 1.9.2, JEI 15.20.0.112 (see plan's risk gates). Large optional/soft-dep tail (REI, EMI, Jade, Create+Ponder+Flywheel+Registrate, Alex's Mobs, Prehistoric Fauna, ~20 Farmer's Delight addons) — all deferred per the plan's Phase 9. Mod entry points: common `FossilMod.init()` (platform-agnostic registry calls) + `ForgeFossilMod`/`FabricFossilMod` per-loader `@Mod`/`ModInitializer` classes (Forge's is the NeoForge seed). 3 mixin JSONs (`fossil_common`/`fossil_forge`/`fossil_fabric.mixins.json`), all `compatibilityLevel: JAVA_17` (needs bump to 21); wired via Loom's `mixinConfig` build.gradle helper on the source side — NeoForge has no such helper, needs a manifest `MixinConfigs` entry or NeoForge's mixin-connector instead. Datagen exists only on the Forge module (`forge/.../forge/data/DataGenerators.java` + ~12 provider classes) — this is the direct seed for NeoForge datagen since Fabric never had any. Not covered by any existing provider: sounds.json, dimension_type JSON, biome-modifier JSON (Forge-format only in source), pack.mcmeta/lang — worth datagenning some of these fresh in the NeoForge port rather than hand-authoring again.
