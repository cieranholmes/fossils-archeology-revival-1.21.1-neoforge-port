Derived from getting Tyrannosaurus fully spawnable/renderable ([[fossils-phase4-entities-progress]], task #10). Use this checklist for every remaining species in task #7 (currently ~60, each backed by a [[fossils-species-port-playbook]]-eligible `StubDinosaur` placeholder in `ModEntities.java`). Most steps are now one-line changes because the shared infrastructure (base classes, generic renderer, AI goal files) already exists — only species-specific pieces need real work.

## The checklist, in order

1. **Species class** (`entity/prehistoric/<Name>.java`, or a subpackage like `swimming/`/`flying/`/`fish/` matching the source layout). Read the 1.20.1 source file in full and port near-verbatim: package rename, and apply the known API-drift catalog in [[fossils-phase4-entities-progress]] (defineSynchedData builder pattern, `getScale()`/`getAgeScale()` split, `MobType` removal, `canBreatheUnderwater`→`canDrownInFluidType`, etc.) as needed. Most simple species (like Tyrannosaurus) need **zero** drift fixes beyond the package rename — the drift lives in the base classes they extend, already ported.
2. **Swap the `StubDinosaur` factory** in `ModEntities.java`: change that one species' `registerDino`/`registerAquatic`/`registerFish` call from `StubDinosaur::new` to `<Name>::new`, and update its `DeferredHolder<EntityType<?>, EntityType<StubDinosaur>>` field type to `EntityType<<Name>>`. Nothing else in `ModEntities.java` needs touching for that species.
3. **Attributes**: add `event.put(<NAME>.get(), Prehistoric.createAttributes().build())` in `ModEntities.registerAttributes` (or the species' own `createAttributes()` if it overrides, like `Mosasaurus`/`PrehistoricFish` do in source) — **or just leave it in the existing "stub attributes" loop if the species doesn't need custom attributes**, since that loop already registers default `Prehistoric.createAttributes()` for every species by holder, real class or not.
4. **Client renderer**: for the ~55 species using the generic look (no special renderer class in source), add one line in `ClientModEvents.registerRenderers`: `event.registerEntityRenderer(ModEntities.<NAME>.get(), context -> new PrehistoricGeoRenderer<>(context, "<name>", RenderType::entityCutout_or_entityCutoutNoCull))` — check the source `ClientInit.java`'s `registerDino(...)` call for that species to get the exact `RenderType` (cutout vs cutoutNoCull vs solid) and whether it uses `registerFish`/`registerTrilobite` variants (`PrehistoricFishGeoRenderer`, not yet ported — port it the same way as `PrehistoricGeoRenderer` if a fish species is next) instead. Species with a bespoke renderer class in source (`QuaggaRenderer`, `FailuresaurusRenderer`, etc.) need that class ported for real, not this one-liner — check `common/.../client/renderer/entity/` for a `<Name>Renderer.java` before assuming the generic path applies. Remove that species from the placeholder-loop in `ClientModEvents` once it has a real registration (it's technically harmless to leave both, but the placeholder line becomes dead/shadowed — cleaner to remove it).
5. **Assets** — copy straight from source, no content changes needed (verified: none of these JSONs embed a `fossil:`-namespaced string that needs rewriting internally, only the *path* changes from `fossil` to `fossils`):
   - `data/fossil/entity_info/<name>.json` → `data/fossils/entity_info/<name>.json`
   - `data/fossil/hitboxes/<name>.json` → `data/fossils/hitboxes/<name>.json` (skip if the species has no multi-part hitbox — check source has the file first)
   - `data/fossil/animations/entity/<name>.animation.json` → `data/fossils/animations/entity/<name>.animation.json` (server-side copy, read by `ServerAnimationInfoLoader`)
   - `assets/fossil/animations/entity/<name>.animation.json` → `assets/fossils/animations/entity/<name>.animation.json` (client-side GeckoLib raw animation, read by GeckoLib itself)
   - `assets/fossil/animations/entity/data/<name>.json` → `assets/fossils/animations/entity/data/<name>.json` (blocks-per-second metadata, read by `ClientAnimationInfoLoader`)
   - `assets/fossil/geo/entity/<name>.geo.json` → `assets/fossils/geo/entity/<name>.geo.json`
   - `assets/fossil/textures/entity/<name>/*.png` → `assets/fossils/textures/entity/<name>/*.png` (all gender/age/sleeping variants — copy the whole directory)
   - Sounds: check `ModSounds.java` already has `<NAME>_AMBIENT`/`_HURT`/`_DEATH`(/`_WEAK`) registered (most species already do, added in an earlier phase) — if so just copy the referenced `.ogg` file(s) from `assets/fossil/sounds/...` to `assets/fossils/sounds/...` at the exact path the sound registration name implies, and add/extend the matching entries in `assets/fossils/sounds.json` (create the file if it doesn't exist yet — it didn't for Tyrannosaurus). Copy the source's `sounds.json` entry for that species verbatim except `fossil:` → `fossils:` in the `sounds` array paths and `subtitle.fossil.` → `subtitle.fossils.` (the lang keys already use `fossils.` — check `en_us.json`, they're usually already present since a much earlier phase added the full lang file).
6. **Food/order-item/other Item-typed fields**: if the species' `getOrderItem()` returns something other than a shared item (`ModItems.SKULL_STICK` for Tyrannosaurus, already added), check whether that item exists in `ModItems.java` yet — most don't (Phase 2/Items is paused). Add a minimal `Item`/`DescriptiveItem` registration for it following the pattern already used for `SKULL_STICK`/`WHIP`/`SCARAB_GEM`/etc., or temporarily fall back to a vanilla placeholder (`Items.STICK`) and flag it, matching the `StubDinosaur` convention — **don't block the whole species port on unrelated Items-phase work**.
7. **Compile, then boot-test**: `./gradlew compileJava` first (catches missing symbols fast), then verify live via the RCON approach in [[fossils-phase4-entities-progress]] rather than trying to pipe stdin into `runServer` (that doesn't work in this harness — see that memory for why and the working alternative): boot `./gradlew runServer --console=plain < /dev/null` in the background with `enable-rcon=true`/`rcon.password=` set in `run/server.properties`, then use the ~40-line Python RCON client to `/summon fossils:<name>` and `/data get entity @s` to confirm attributes/NBT populate correctly. Then boot `./gradlew runClient --console=plain < /dev/null` and watch its log for `FATAL`/`Game crashed`/`BUILD FAILED` (or, if a human is available, they can eyeball the actual render — that's how Tyrannosaurus's renderer bugs got caught, the log alone wouldn't have surfaced "backwards texture" type issues).
8. **Delete `run/world` and `run/saves/*`** before a clean boot-test if the world was previously used to summon test entities of a species that then changed shape/renderer — otherwise old saved entities from a stale registration can crash the client on load with a null-renderer NPE that has nothing to do with the current species being tested (this exact false alarm happened once during the Tyrannosaurus slice, caused by a leftover un-rendered `dinosaur_egg`/earlier-summoned entity from RCON testing, not by anything wrong with the current code).

## What's already shared infrastructure (don't re-port per species)

- `Prehistoric`, `PrehistoricLeaping`/`Swimming`/`Flying`/`Flocking`/`Fish`/`SwimmingBucketable`, `PrehistoricEntityInfo`, `Gender`, `OrderType`, `PrehistoricMobType`/`MoodType`, variant/ package — Task #4/#5, done.
- Most `entity/ai/` goal files a normal land dino needs (`DinoWanderGoal`, `DinoPanicGoal`, `DelayedAttackGoal`, `DinoFollowOwnerGoal`, `HuntingTargetGoal`, `DinoMatingGoal`, `Eat*Goal`/`MoveToFoodGoal`/`CacheMoveToBlockGoal`, `PlayGoal`, target goals) — done, see [[fossils-phase4-entities-progress]] task #10 section for the full list. Swimming-species goals (`GrabMeleeAttackGoal`, `WaterPlayGoal`, `EnterWaterGoal`, `DinoRandomSwimGoal`, `AmphibiousWanderGoal`) and flying-species goals (`Flying*Goal`s) are also done. Only ~8 of the original 32 remain (species-specific outliers — check task #6 in the live TaskList before assuming one is missing).
- `client/model/PrehistoricGeoModel.java`, `client/renderer/entity/PrehistoricGeoRenderer.java` — the shared GeckoLib renderer/model pair every non-bespoke-renderer species uses. Done.
- `FoodMappings`/`Diet`/`FoodType`, `FeederBlockEntity` (feeding logic, minus the still-missing `BlockEntityTicker` hookup) — done, generic vanilla-mapping only (no per-species food values yet, that's `FossilFoodMappings.register()`, not ported).
- `ToyBase`/`ToyBall` — done (`ToyBall.getPickResult()` is a placeholder pending `ModItems.TOY_BALLS`).

## What's still genuinely per-species work every time

- The species class itself (behavior/animation overrides, even if usually small).
- Assets (step 5 above) — always per-species, no way around copying textures/geo/animations.
- Any bespoke renderer class (rare — most use the generic one).
- Order item / other `Item`-typed fields not yet in `ModItems.java`.
- Food values for that species (`FossilFoodMappings`'s per-species loop, not ported — currently every species falls back to the generic vanilla-animal heuristic in `FoodMappings.getMobFoodPoints`).
