## What was ported

New package `src/main/java/com/github/fossil/data/loot/`: `ModBlockLootTables.java`, `ModEntityLootTables.java`, `ModGenericLootTables.java` — mechanical port of the source repo's `forge/.../forge/data/loot/` classes. ## Key 1.21.1 API-drift decisions (extends [[fossils-phase7-recipes-datagen-research]])

- **Loot table keys became `ResourceKey<LootTable>`, not `ResourceLocation`** — `LootTableSubProvider.generate(BiConsumer<ResourceKey<LootTable>, LootTable.Builder>)`, `Block.getLootTable()`/`EntityType.getDefaultLootTable()` all return `ResourceKey<LootTable>` now. `LootTableReference` (source) was renamed/replaced by `NestedLootTable.lootTableReference(ResourceKey<LootTable>)`. `DynamicLoot.dynamicEntry(ResourceLocation)` is unchanged (tag-entry weight dynamic drops still take a bare `ResourceLocation`).
- **`BlockLootSubProvider`/`EntityLootSubProvider` constructors gained a `HolderLookup.Provider registries` param**, stored as a `protected final` field — needed because enchantment/fortune references now resolve through the dynamic registry rather than being static objects. `LootTableProvider.SubProviderEntry` is `Function<HolderLookup.Provider, LootTableSubProvider>` (was a bare `Supplier` in 1.20.1), so sub-providers needing no registries (`ModGenericLootTables`) are wired via `registries -> new ModGenericLootTables()`, not a bare constructor reference.
- **`LootingEnchantFunction` renamed to `EnchantedCountIncreaseFunction`**, and its `lootingMultiplier` factory gained a `HolderLookup.Provider registries` first param (to resolve the `Enchantments.LOOTING` holder internally).
- **`ItemPredicate.Builder.hasEnchantment(...)` is gone** — replaced by `.withSubPredicate(ItemSubPredicates.ENCHANTMENTS, ItemEnchantmentsPredicate.enchantments(List.of(new EnchantmentPredicate(Holder<Enchantment>, MinMaxBounds.Ints))))`, mirroring vanilla's own `BlockLootSubProvider.hasSilkTouch()`. `EnchantmentPredicate`/`ApplyBonusCount.addOreBonusCount`/`addUniformBonusCount` all now take `Holder<Enchantment>`, not the enchantment object directly — resolved via `registries.lookupOrThrow(Registries.ENCHANTMENT).getOrThrow(key)`.
- `Enchantments.BLOCK_FORTUNE` (source, 1.20.1) → `Enchantments.FORTUNE` (1.21.1 vanilla rename; also now a `ResourceKey<Enchantment>`, not a Forge-registered object).
- `AbstractGlassBlock` (source's superclass check for "any glass block drops itself with silk touch") **no longer exists in 1.21.1 vanilla** — merged into `TransparentBlock`. This repo's own `ClearGlassBlock` (ported in an earlier phase) extends `Block` directly, not `TransparentBlock`, so the loot check became `instanceof ClearGlassBlock` instead — confirmed via grep that no other glass-family class exists yet in this repo.
- `DeferredBlock`/`DeferredItem`/`DeferredRegister` iteration: source's Architectury `RegistrySupplier.ifPresent(...)`/`.spliterator()` idioms → direct `.get()` calls (DeferredBlock/Item always resolve post-registration in this NeoForge-only project, established since [[fossils-phase7-task3-blockstate-item-providers]]) and `DeferredRegister.getEntries().stream()`/`for (var entry : X.getEntries())` (no `Iterable`/`spliterator()` on `DeferredRegister` itself).

## The enchantment-registry rabbit hole (the real scope surprise in this task)

`fossil:archeology`/`fossil:paleontology` are datapack-JSON-only enchantments (per [[fossils-phase2-items-progress]] — `ModEnchantments` is just `ResourceKey<Enchantment>` constants, actual definitions live at `data/fossil/enchantment/{archeology,paleontology}.json`). Datagen's `HolderLookup.Provider` (`GatherDataEvent.getLookupProvider()`) is built by vanilla's `VanillaRegistries::createLookup`, a **pure-Java bootstrap registry set** (`net.minecraft.world.item.enchantment.Enchantments::bootstrap` for `Registries.ENCHANTMENT`) that never reads mod resource JSON — so any datagen code resolving `fossil:archeology` (this loot table's `enchant()` helper) threw `Missing element ResourceKey[minecraft:enchantment / fossil:archeology]` at `generate()` time, and a naive `Holder.Reference.createStandAlone(...)` fallback (tried first, to avoid a whole new provider) got past `generate()` but then failed at JSON-serialization time with `"is not valid in current registry set"` (`LootTable.DIRECT_CODEC`'s `RegistryFixedCodec` for `Holder<Enchantment>` validates registry membership at encode time, not just at read time).

**Real fix**: new `com.github.fossil.enchantment.ModEnchantmentProvider.bootstrap(BootstrapContext<Enchantment>)`, field-for-field mirroring the two JSON files (`Enchantment.definition(items.getOrThrow(ItemTags.MINING_LOOT_ENCHANTABLE), 1, 3, Enchantment.dynamicCost(1, 10), Enchantment.dynamicCost(51, 10), 8, EquipmentSlotGroup.MAINHAND)`, cross-referencing `exclusiveWith(HolderSet.direct(silk_touch, the-other-one))` — forward-referencing the not-yet-registered sibling enchantment via `context.lookup(Registries.ENCHANTMENT)` works fine, same as vanilla's own cross-referencing exclusive sets). Wired into `DataGenerators.gatherData` via `event.createDatapackRegistryObjects(new RegistrySetBuilder().add(Registries.ENCHANTMENT, ModEnchantmentProvider::bootstrap))`, called **before** capturing `event.getLookupProvider()` (that call populates `GatherDataEvent.registriesWithModdedEntries`, which `getLookupProvider()` then returns instead of the vanilla-only default). Diffed the generated JSON output against the hand-authored files — content matches exactly (only key ordering differs, since the codec alphabetizes). **The hand-authored JSON files remain the actual shipped source of truth**; this bootstrap exists solely so datagen's registry set is populated, and is not itself wired as a real `DatapackBuiltinEntriesProvider` output we keep (that provider's `src/generated` output was deleted after verification, same as every other datagen run this project does).

## Another silent bug caught only by a real `runData` run (not compile)

`TAR` (`ModBlocks.java`) is a `LiquidBlock` built via `Properties.ofFullCopy(Blocks.WATER)`, which carries vanilla's `.noLootTable()` — so `TAR.getLootTable()` is already `BuiltInLootTables.EMPTY`. Source's `NO_TABLE.forEach(block -> add(block, noDrop()))` unconditionally added an explicit map entry for every `NO_TABLE` block including TAR; `BlockLootSubProvider.generate()`'s final loop explicitly skips blocks whose loot-table key is `EMPTY`, so that entry was never consumed, tripping `"Created block loot tables for non-blocks: [minecraft:empty]"` at the very end of `generate()`. Fixed by skipping `add()` for any `NO_TABLE` block whose `getLootTable()` is already `BuiltInLootTables.EMPTY`.

## Deviations forced by target-repo drift (not stylistic — verified independently, not just agent-claimed)

1. **`HOME_PORTAL` dropped from `NO_TABLE`** — doesn't exist in target `ModBlocks.java` yet (confirmed absent, consistent with [[fossils-phase7-task3-blockstate-item-providers]]/[[fossils-phase7-task4-tags-providers]]). `OBSIDIAN_SPIKES` was never in source's `NO_TABLE` list to begin with (that name only appeared in the tags-provider skip list from task 3/4, unrelated to this file).
2. Custom `ModLootProvider.validate(...)` override (present in source, manually re-implementing per-table validation) was **dropped** — 1.21.1 vanilla's own `LootTableProvider.validate(...)` default already does the equivalent full-holder validation; the source override was redundant even before the port, and re-implementing it against the new `WritableRegistry`/`ProblemReporter.Collector` signature would have been pure duplication.
