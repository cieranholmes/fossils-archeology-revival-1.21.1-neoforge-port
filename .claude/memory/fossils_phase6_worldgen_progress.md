## Key architectural finding (reusable for Phase 7 too)

Most of the source's Phase-6 "Mod*" classes (`ModStructures`, `ModStructureSets`, `ModTemplatePools`, `ModOreFeatures`, `ModBiomes`, `ModConfiguredFeatures`, `ModPlacedFeatures.bootstrap`, `ModOrePlacements`, `ModDimensions.bootstrap`) are **`BootstapContext<T>` datagen-bootstrap methods, not runtime code** — they only exist to produce the JSON already sitting in the source's `common/src/generated/resources/data/fossil/worldgen/` tree. Since this project's datagen pipeline isn't stood up yet (that's Phase 7), the pragmatic approach — same one already used for one Phase-4 damage_type JSON — was to **copy the already-generated JSON directly** (renaming the `fossil`→`fossils` namespace) instead of porting these classes as real Java. Real runtime code was only written for the handful of things that need a live `ResourceKey`/codec at server-run time (chunk generators needing biome/structure keys, `AnuCastleStructure`'s custom jigsaw placement, the TerraBlender region). Where a real key was still needed, minimal "keys-only" classes (same names as source, stripped of the bootstrap method) were created: `world/biome/ModBiomes.java`, `world/feature/structures/ModStructures.java`.

### 3 real bugs found and fixed via this testing (not caught by compilation)

1. **`Registry.register(BuiltInRegistries.STRUCTURE_TYPE/CHUNK_GENERATOR, ...)` inside `FMLCommonSetupEvent` (even in `enqueueWork`, even directly in the mod constructor) throws `IllegalStateException: Registry is already frozen`.** These two are "simple" code registries (not data-driven) that NeoForge only unfreezes for the duration of `RegisterEvent`'s dispatch for that specific registry key — frozen everywhere else. **Fix**: moved both registrations into a `modEventBus.addListener((RegisterEvent event) -> { event.register(Registries.STRUCTURE_TYPE, helper -> {...}); event.register(Registries.CHUNK_GENERATOR, helper -> {...}); })` listener. `ModStructureType`'s 3 fields became plain unregistered `StructureType<S>` lambda instances (`() -> AnuCastleStructure.CODEC` etc.) since the actual `Registry.register` call now lives in the `RegisterEvent` handler, not in a static field initializer. **Reusable lesson**: any future code needing `BuiltInRegistries.X.register(...)` for a "simple" (non-data-driven) registry must use `RegisterEvent`, never `FMLCommonSetupEvent` — the two are easy to conflate since both "feel like" generic late-init hooks, but only `RegisterEvent` gets the unfreeze window.
2. **Structure NBT templates must live under `data/<ns>/structure/` (singular), not `data/<ns>/structures/` (plural).** The 1.20.1 source mod used the plural folder (an actual 1.20.1 vanilla convention), but 1.21.1's `StructureTemplateManager.RESOURCE_LISTER` is hardcoded to `new FileToIdConverter("structure", ".nbt")` (singular) — confirmed both by reading the decompiled class AND by checking that vanilla's own shipped structure NBTs (bastion pieces etc., extracted from the real server jar) live under `data/minecraft/structure/`. **The failure mode is silent**: `StructureTemplateManager.tryLoad` catches ALL exceptions with an empty `catch (Exception e) {}` (no logging) and falls back to a brand-new blank `StructureTemplate()`, which produces a degenerate ~1×1×1 bounding box and zero jigsaw blocks — `structureStart.isValid()` still reports `true` and 1 "piece" gets recorded, so nothing crashes or warns; the structure just silently fails to actually place any blocks. **If a future phase adds more structure NBT and it silently doesn't appear in-game, check this folder name FIRST** before assuming a placement-logic bug — this cost the most debugging time in this session precisely because it fails so quietly. Fixed by `mv`-ing the whole `data/fossils/structures/` directory to `data/fossils/structure/` (all 65 files, one move, no NBT content changes needed).
3. **`ComfyBedBlock` (a `BedBlock` subclass, ported in Phase 1) crashes when placed via a structure template**, with `IllegalStateException: Invalid block entity minecraft:bed ... got Block{fossils:comfy_bed}`. Root cause: vanilla `BedBlockEntity`'s constructors hardcode `super(BlockEntityType.BED, ...)`, and `BlockEntityType.BED`'s valid-blocks whitelist is a fixed set of the 16 vanilla dye-colored beds baked in at class-init — `fossils:comfy_bed` was never added to it (it can't be, post-hoc). This mismatch is invisible during normal in-game block placement (players just placing the block) but structure-template placement explicitly validates the live block entity's type against what's recorded in the NBT and throws on mismatch. **Fix** (a real, narrow, NeoForge-documented pattern — see the "Neo: always use getType()" comment NeoForge itself added to `BlockEntity`): created `ComfyBedBlockEntity extends BedBlockEntity` overriding the non-final `getType()` to return a newly-registered `ModBlockEntities.COMFY_BED` type instead of the inherited `BlockEntityType.BED`; overrode `ComfyBedBlock.newBlockEntity(...)` to construct it; registered a renderer reusing vanilla's `BedRenderer` directly (works unchanged since it's typed to `BedBlockEntity` and our class still extends it — only `getType()` differs). **This is a Phase-1-era bug that Phase 6 happened to be the first thing to actually exercise** (no prior phase ever placed a comfy_bed via structure NBT) — worth flagging in [[fossils-known-upstream-bugs]] as a *found-in-target* bug (not carried over from source) if that memory gets revisited, since it's a NeoForge-version-specific gotcha, not something present in the 1.20.1 source at all.

### Immediate follow-up, same day: fluid crash was fixed but the tar texture was STILL missing (2nd real user report)

After the `IClientFluidTypeExtensions` fix above, the user confirmed the crash was gone but the tar fluid rendered with **no texture at all**. Root cause was a second, independent gap in the exact same area — **`ModBlocks.TAR` (the placed `LiquidBlock`, a `TarBlock` subclass) is missing its blockstate + block-model JSON.**

`TarBlock.getRenderShape()` deliberately overrides to return `RenderShape.MODEL` (faithfully ported from source, not a mistake) instead of vanilla `LiquidBlock`'s `RenderShape.INVISIBLE`. Mechanism (traced through decompiled 1.21.1 `SectionCompiler`/`ItemBlockRenderTypes`/`ModelBakery`): a block with fluid state gets rendered via **two independent passes** — the fluid-quad pass (fixed by the `IClientFluidTypeExtensions` registration) AND, separately, a normal block-model pass gated purely on `getRenderShape() == RenderShape.MODEL`, regardless of whether the block also has a fluid state. Since `RenderShape.MODEL` requires an actual model to exist, and no `assets/fossils/blockstates/tar.json`/`assets/fossils/models/block/tar.json` existed anywhere in the port, `ModelBakery` fell back to its hardcoded missing-model mesh (`MissingTextureAtlasSprite` on every face) for that second pass — an opaque magenta/black checkerboard cube occupying the exact same space as the (now correctly rendering) fluid underneath, i.e. exactly what "missing texture" looks like.

The source's 1.20.1 build **did** ship both files (found under its Forge module's `src/generated/resources`, i.e. this was datagen output, same pattern as several other Phase-6-era gaps in this file): the model has **zero elements/parent** — it exists only so model lookup succeeds and to supply a particle/dig-texture (`"particle": "fossil:block/tar_still"`), not to render an actual cube (the fluid pass does all the real rendering). **Fix**: added the same 2 files, namespace-renamed, no datagen needed since these are trivial:
- `assets/fossils/blockstates/tar.json`: `{"variants":{"":{"model":"fossils:block/tar"}}}`
- `assets/fossils/models/block/tar.json`: `{"textures":{"particle":"fossils:block/tar_still"}}`

Verified: `runClient` boots clean, no "missing model"/"no blockstate" warnings for `fossils:tar` in the log. **Same caveat as the crash fix** — I can't drive the actual "look at a tar block in person" repro step from here, so this needs the user's confirmation on next playtest, not just log absence-of-warnings.

**Not investigated, flagged as a possible follow-up if tar still looks visually off after this fix**: no fluid render-layer (`ItemBlockRenderTypes.setRenderLayer`) was ever registered for tar, in source OR target — unregistered fluids default to `RenderType.solid()` (same as lava, which also isn't registered), so this is very likely intentional/harmless (matches lava's fully-opaque look), not a gap — but if tar is *supposed* to look glossy/translucent and doesn't, that would be the next thing to check. Also noted: both tar PNGs are RGB (no alpha channel) — fine for an opaque appearance, would matter only if translucency is later added.

### Reusable RCON/debugging techniques from this session (beyond the established RCON-client pattern from Phase 4)

- **`/data get block <pos>` only works on block ENTITIES** — for checking whether an arbitrary block is air/non-air over RCON (which has no direct "read blockstate" command), use `/execute if block <pos> minecraft:air run <any-command-with-visible-output>` (e.g. `run seed`) as a boolean probe: output present = condition true, no output = condition false. Commands like `/say` produce **no RCON response at all** even when they run successfully — don't use them as truthiness probes, they'll look identical to a false condition.
- **`/forceload add` alone is not enough to test wide-spanning structures** — it only generates the chunks you explicitly list (plus vanilla's small automatic neighbor-generation radius, ~1 chunk). A structure spanning 70+ blocks needs forceloading a correspondingly wide chunk range, or `applyBiomeDecoration`/`createReferences` will simply never fire for the chunks the structure actually occupies, and it'll look like nothing generated even though the structure start itself is valid.
- **Temporary `LOGGER.warn("PHASE6_DEBUG ...")` lines directly in the generation methods being tested (`createStructures`/`applyBiomeDecoration`/`addPieces`/`tryPlacingChildren`), removed after diagnosis** were what actually cracked bugs #1 and #2 above — `structureStart.getPieces().size()` and the piece's `getBoundingBox()` before/after `move()` were the two most informative single values. Silent-fallback failure modes (like bug #2's empty-catch) are otherwise invisible from server logs alone.
- **The bundled `minecraft_1.21.1_server.jar` in NeoFormRuntime's artifact cache is a *bundler* jar, not the real content jar** — it only has ~139 entries (manifest + nested library jars). The actual game code/resources (including vanilla's own shipped structure NBTs, used here to build the village house-pool JSON overrides) are nested inside at `META-INF/versions/1.21.1/server-1.21.1.jar`. Extract that inner jar before grepping for any vanilla resource path.
