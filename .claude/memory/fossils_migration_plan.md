Full-mod migration plan, produced 2026-08-09 from a parallel catalog of every subsystem in the source repo (`~/Personal/FossilsArcheologyRevival` - moved from the `~/IdeaProjects/FossilsArcheologyRevival` path this memory originally recorded; don't confuse with the unrelated stale copy under a different home dir at `~cieranholmes1/IdeaProjects/FossilsArcheologyRevival`). See [[project-neoforge-port]] for the standing decision this builds on (NeoForge-only, no common/forge/fabric split, mod id stays `fossils`/`com.github.fossils`). See [[fossils-migration-inventory]] for the raw per-subsystem scale/catalog this plan was derived from.

**Why this plan exists:** the source mod is large (~1000+ Java files across common/forge/fabric) and two migrations are happening at once — dropping Architectury/Fabric, and jumping MC 1.20.1→1.21.1. Porting file-by-file in source order would hit the hardest architectural rewrites (capabilities, GeckoLib, worldgen) before establishing whether the mod's core external dependencies even have NeoForge 1.21.1 builds. This plan sequences work to surface blocking risks first and defers high-effort/low-value work (Fabric-only code, triple recipe-viewer integrations, debug tooling) to the end or drops it outright.

**How to apply:** when the user asks to continue the port, check which phase is in progress (read the target repo's current state — this plan doesn't track live completion status) and work through that phase's items in the given order. Don't skip Phase 0's dependency spike for later phases that depend on it (entities/client rendering are gated on GeckoLib + more-hitboxes; worldgen's volcano biome is gated on the TerraBlender decision).

## Dependency policy (decided 2026-08-09, overrides earlier "drop it" instincts below where noted)

Two distinct tiers exist in the source `build.gradle` — don't conflate them:

- **Hard dependencies** (`modImplementation`, listed in `mainFile.addRequirement` on both loaders): **GeckoLib, TerraBlender, more-hitboxes**, plus Architectury. The mod does not load/function without these. Architectury is the only one being dropped (it's multi-loader glue, meaningless once NeoForge-only per [[project-neoforge-port]]) — GeckoLib/TerraBlender/more-hitboxes stay, just bumped to 1.21.1 versions. This is the real Phase 0 gate.
- **Optional compat integrations** (`modCompileOnly`, or `Platform.isModLoaded()`-guarded code): **JEI, EMI, REI, Farmer's Delight + its ~20 addon mods, Create/Ponder/Flywheel/Registrate, Alex's Mobs, Prehistoric Fauna**. The mod runs fine without any of these — they just add optional tooltip/recipe-viewer/crossover integrations when present. Jade is a borderline case (`modImplementation` on the Forge side specifically, `modCompileOnly`+`modRuntimeOnly` on Fabric) but functionally it's the same kind of plugin, not something the base mod needs. **User's call: keep and version-bump the compat tier too, don't prune it to reduce scope** — but treat it as Phase 9 scope, not a Phase 0 gate, since none of it blocks the mod from loading or the earlier phases from proceeding.

**Version availability, checked 2026-08-09 (re-verify at actual build time — these mods ship frequently):**
- **GeckoLib** (hard dep) — confirmed available for NeoForge 1.21.1, versions 4.7–4.9.2 (latest seen: 4.9.2). Source uses 4.7.2, so this is a **minor bump within the 4.x line, not the 4→5 major-version jump previously assumed in this plan** — still expect real API drift (GeckoLib does churn `CoreGeoBone`/renderer internals between minors) but it's smaller than a major-version rewrite. Re-verify exact API diffs against whichever 4.9.x point release is current when Phase 4/5 starts.
- **TerraBlender** (hard dep) — confirmed available for NeoForge 1.21.1 (4.1.0.8 and later). Port it directly; do NOT redesign the volcano biome away from TerraBlender.
- **more-hitboxes** (hard dep, `com.github.darkpred.morehitboxes`) — confirmed available for NeoForge 1.21.1 (1.9.3-alpha). Multi-hitbox support for all dinosaurs is unblocked.
- **JEI** (compat) — confirmed widely available for NeoForge 1.21.1 (19.2x–19.3x line as of this check).
- **Jade** (compat) — confirmed available for NeoForge 1.21.1 (15.10.x).
- **REI** (compat) — confirmed available for NeoForge 1.21.1.
- **Farmer's Delight** (compat) — confirmed official NeoForge 1.21.1 builds exist (1.3.x line).
- **EMI, Create/Ponder/Flywheel/Registrate** (compat) — not individually confirmed in this check; both are popular/actively-maintained and near-certainly have 1.21.1 NeoForge builds, but verify each specifically before wiring up that compat in Phase 9.
- **Alex's Mobs** (compat) — ⚠️ the *official* mod has no 1.21.1 build; only an **unofficial community NeoForge port** exists (`gblfxt/AlexsMobs-Neoforge`), which itself depends on an unofficial "Citadel" port. Flag this to the user before committing to it in Phase 9 — it's a materially different trust/maintenance situation than the other deps, not a straightforward version bump.
- **Prehistoric Fauna** (compat) — ⚠️ no evidence of any 1.21.1 (or NeoForge) build found; latest visible activity targets 1.20.1. This compat integration may simply have nothing to depend on — treat as likely-dropped by necessity, not by choice, and confirm directly with the user once Phase 9 is reached rather than assuming.
- **~20 individual Farmer's Delight addon mods** (compat, BYG, Ars Nouveau, Brewin' & Chewin', the various "X's Delight" packs, etc.) — not checked individually; each needs its own availability check when that specific addon's compat class is actually being ported in Phase 9. Don't assume the whole tail is available just because Farmer's Delight itself is.

## Top risk gates (check before investing in the phase that depends on them)

1. **GeckoLib version drift (hard dep).** Source is deeply coupled: `Prehistoric` (the base class for ~65 dinosaur/fish entities) directly implements GeckoLib's `GeoEntity`/animatable interfaces, plus 4 mixins (`AnimationControllerMixin`, `AnimationProcessorMixin`, `AnimatableManagerAccessor`, `AnimationControllerAccessor`) reach into GeckoLib's internal fields, plus 2 more mixins (`GeoEntityRendererMixin`, forge+fabric) target exact GeckoLib method descriptors for riding/vehicle interpolation. The actual jump is 4.7.2→~4.9.x (same major line), smaller than originally feared, but every one of ~15+ renderer/model classes and all 4+ internals-reaching mixins still need re-verification against the specific 4.9.x point release used — not just recompilation. **Still the biggest single risk in the migration**, just a smaller one than first assessed.
2. **more-hitboxes (hard dep)** — resolved: NeoForge 1.21.1 build confirmed (1.9.3-alpha). Still verify the multi-part-hitbox API itself hasn't changed shape before porting `Prehistoric`/`PrehistoricSkeleton`.
3. **TerraBlender (hard dep)** — resolved: NeoForge 1.21.1 build confirmed (4.1.0.8+). Port directly; volcano biome swap stays as-is, no redesign needed.
4. **Namespace/modid sweep.** Source uses mod id `fossil` / package `com.github.teamfossilsarcheology.fossil`; target keeps `fossils` / `com.github.fossils` (user's explicit choice). Every ported asset path, tag namespace (`#fossil:` → `#fossils:`), hardcoded mod-id string, and resource location needs renaming during the port — don't copy-paste source Java/JSON verbatim.
5. **Alex's Mobs / Prehistoric Fauna compat availability (Phase 9, non-blocking)** — see dependency policy above; these two are the only compat items where "just bump the version" may not be possible. Surface this to the user at Phase 9, don't silently drop or silently assume availability.

## Cross-cutting architecture decisions (apply throughout, not phase-specific)

- **Registration:** every `dev.architectury.registry.registries.DeferredRegister`/`RegistrySupplier` becomes NeoForge's native `DeferredRegister`/`DeferredHolder`. Mechanical, touches nearly every registry-holder class (`ModBlocks`, `ModItems`, `ModEntities`, `ModBlockEntities`, `ModMenus`, `ModRecipes`, `ModSounds`, `ModFluids`, `ModEnchantments`, `ModVillagers`, `ModLootItemFunctionTypes`, etc.).
- **Per-loader "Impl" pairs collapse to one class, seeded from the Forge side** (NeoForge is Forge's spiritual successor, so the Forge implementation is almost always the closer starting point than the Fabric one). Confirmed pairs across the whole codebase: `block/custom_blocks/{forge,fabric}` (3 blocks: FossilLeaves, FlammableRotatedPillar, Tar), `item/{forge,fabric}` (6 block-item renderer shims), `capabilities/{forge,fabric}` (energy+mammal/first-hatch data), `world/dimension/{forge,fabric}` (teleporter), `world/feature/{forge,fabric}` (ModFeaturesImpl), `world/feature/village/{forge,fabric}`, `block/{forge,fabric}` (ModWoodTypesImpl, ModBlockSetTypesImpl), `config/{forge,fabric}`, `util/{forge,fabric}` (VersionImpl), `compat/emi/{forge,fabric}`, `compat/jade/{forge,fabric}`, `client` plant-model-loader (Forge `IModelGeometry`/`IModelLoader` — use this side, not Fabric's).
- **@ExpectPlatform disappears entirely** — every one of the above collapses to a single concrete class, no more platform-expectation indirection.
- **Capabilities: total rewrite, not mechanical port.** Forge 1.20.1's `Capability<T>`/`LazyOptional` + mixin-injected `getCapability()` override (`EnergyContainerBlockEntityMixin`, `MachineContainerBlockEntityMixin`) has no direct equivalent — NeoForge 1.21.1 uses `RegisterCapabilitiesEvent` + `net.neoforged.neoforge.capabilities.Capabilities.EnergyStorage/ItemHandler` registered per block-entity-type, no mixin needed at all. This is a net simplification once done, but it's a rewrite of the bridging layer from scratch.
- **Player/entity "capability" data → NeoForge Data Attachments.** Mammal pregnancy/embryo state and the "has hatched a dinosaur" player flag currently ride on Forge's real capability system; port these to NeoForge's `AttachmentType` API instead (cleaner fit than shoehorning into the block/item capability system above).
- **Networking → CustomPacketPayload.** ~20 hand-rolled packet classes (architectury-networking `NetworkChannel`, manual `FriendlyByteBuf` read/write/apply/register boilerplate) become NeoForge `CustomPacketPayload` records with `StreamCodec`, registered via `PayloadRegistrar`. Mechanical but voluminous.
- **Enchantments → datapack JSON.** Source has 2 Java `Enchantment` subclasses (Archeology, Paleontology) with Java-side `checkCompatibility` overrides — 1.21.1 enchantments are fully data-driven (`Enchantment.enchantment()` builder + `EnchantmentEffectComponents`, `checkCompatibility` becomes an exclusive-set tag). Full rewrite, not a recompile.
- **Loot functions → MapCodec.** `CustomizeToDinoFunction.Serializer` uses the old GSON-based `Serializer` pattern; 1.21 loot functions use `MapCodec`.
- **Fluids → NeoForge-native.** `ModFluids`/`TarFluid` uses Architectury's `ArchitecturyFluidAttributes` with no direct NeoForge equivalent — needs a from-scratch NeoForge fluid definition. Note the `TAR` block in `ModBlocks` depends on `ModFluids.TAR`, so sequence fluids before/alongside the blocks phase.
- **Config → NeoForge ModConfigSpec.** Forge's `ForgeConfigSpec` (already used on the Forge side) ports almost directly; drop the Fabric MidnightConfig path and its 2 dedicated mixins entirely.
- **Mixins: audit every one individually, don't blanket-port.** ~23 common + ~5 forge (fabric's ~6 are dropped entirely). Categories: (a) dev-only debug tooling (`DebugLevelRendererMixin`, `DebugMinecraftMixin`, `DebugMouseHandlerMixin`, `ChunkStatusMixin`) — recommend dropping; (b) capability-bridging (superseded by `RegisterCapabilitiesEvent`, delete); (c) GeckoLib-internal patches — may already be fixed upstream in GeckoLib 5.x, re-verify before porting; (d) genuinely-still-needed vanilla behavior patches (`SyncedEntityDataMixin`, `CatMixin`/`OcelotMixin` dino-fear AI, `NaturalSpawnerMixin`, `ServerEntityMixin` passenger sync, `WalkNodeEvaluatorMixin` fence pathing, `PlayerInfoMixin` cape rendering) — check for a native 1.21.1/NeoForge event first, mixin only if none exists; (e) fragile worldgen mixins (`JigsawPlacementMixin`, `JigsawStructureMixin` — reference obfuscated method names, high breakage risk from the MC version bump alone, independent of loader).

## Phased roadmap

**Phase 0 — Foundations & dependency spike.** Resolve the 3 hard-dependency risk gates above (GeckoLib, more-hitboxes, TerraBlender) — the compat-tier items (JEI, EMI, REI, Jade, Farmer's Delight, Create, Alex's Mobs, Prehistoric Fauna) are Phase 9 scope and don't block this phase. Wire up mixin loading (NeoForge has no Loom `mixinConfig` helper — needs manifest `MixinConfigs` entry or NeoForge's mixin connector), Java 21 mixin compatibility level. Port `FossilMod` (common init) + a single `@Mod` entry class (merge what `ForgeFossilMod` did, using NeoForge's constructor-injected `IEventBus` instead of Architectury's `EventBuses`). Port config (Forge `ForgeConfigSpec` → NeoForge `ModConfigSpec`). No packets, no capabilities yet — goal is an empty-ish mod that loads.

**Phase 1 — Blocks.** Already scoped separately: simple/decorative blocks first, then the 52 custom `Block` subclasses, then the 13 machine block entities last (as data holders — defer capability *exposure* to Phase 3, since that's a NeoForge-native rewrite anyway, not a port of the mixin-based Forge approach).

**Phase 2 — Items, materials, food, fluids, loot, tags, sounds, advancements, villager trades, enchantments.** Port `ModFluids`/`TarFluid` here (or alongside Phase 1, since `TAR` block depends on it). Enchantments and loot functions get full rewrites per the architecture decisions above, not straight ports.

**Phase 3 — Capabilities & networking rewrite.** `RegisterCapabilitiesEvent` for machine energy/item-handler exposure, NeoForge Data Attachments for mammal/first-hatch player data, rewrite all ~20 packets to `CustomPacketPayload`.

**Phase 4 — Entities & AI.** Gated on Phase 0's GeckoLib/more-hitboxes spike. Register `EntityType`s/attributes (mechanical), then port the `Prehistoric` framework itself: AI systems (`MoodSystem`, `SleepSystem`, `LeapSystem`, `SitSystem`), custom navigation/node-evaluators, the variant/skin data-driven system, breeding/aging. This is the single largest chunk of source content (199 files) and the framework port (not per-entity busywork) is where the real effort is.

**Phase 5 — Client rendering. COMPLETE as of 2026-08-13**, see [[fossils-phase5-debug-gui-progress]] for the final sub-task (debug GUI) — that memory's name undersells it, it's the record for all of Phase 5's completion, not just the debug screens. Gated on Phase 4. GeckoLib renderers/models for every entity (biggest client risk per gate #1), block-entity renderers (plain `ModelPart`, lower risk — not GeckoLib-based), armor renderer (`GeoArmorRenderer`), particles, machine GUIs/screens (low risk, simple `AbstractContainerScreen`s), the Dinopedia encyclopedia screen. **Deviation from this plan's original recommendation:** this line originally suggested dropping the debug/pathing-visualization GUI subsystem (dev-only, ~15 files) rather than porting it — the user chose to port it instead, and it's now fully done (34 files total once the `navigation`/`instruction` subpackages are counted), with one deliberate remaining gap: the world-space debug-render hooks depend on a mixin framework this project doesn't have (see that memory for details) - dev-tooling only, no gameplay impact.

**Phase 6 — World generation.** Next phase up (Phase 5 is complete). Biomes, structures (`AnuCastleStructure`, `HellBoatStructure`, `TreasureRoomStructure` — custom `Structure` subclasses with real generation logic, not just jigsaw JSON), custom `ChunkGenerator`s (`AnuLairChunkGenerator`, `TreasureChunkGenerator` — override low-level abstract methods that change signature release-to-release, expect rewrites not recompiles), features, trees, the two custom dimensions. This is disruptive from the MC version bump alone, independent of the loader change. **Risk gate #3 (TerraBlender) is resolved, not open** — NeoForge 1.21.1 build confirmed (4.1.0.8+) back in Phase 0, so despite this line's original wording there is no volcano-biome redesign to do: port the volcano biome directly on TerraBlender like every other biome, per the dependency-policy section above.

**Phase 7 — Recipes & datagen.** Recipe types/serializers are low-risk (vanilla-shaped, port near-unchanged). Stand up NeoForge datagen mirroring the source's Forge-only datagen module (Fabric had none, so Forge's `ModBlockStateProvider`/`ModBlockModelProvider`/`ModItemProvider`/tag providers/`ModRecipeProvider`/`ForgeAdvancementProvider`/`ModLootProvider`/`ModWorldGenProvider`/`ModFoodValueProvider` is the direct seed). Also datagen the biome-modifier JSON (source only generated this for Forge; Fabric relied on runtime code) and consider datagenning dimension_type/sounds rather than hand-authoring.

**Phase 8 — Mixin cleanup pass.** Apply the per-mixin audit from the architecture decisions above now that the surrounding systems (capabilities, entities, worldgen) are ported and it's clear what's actually still needed.

**Phase 9 — Compat integrations.** Per the dependency policy above, port all three recipe-viewer integrations (JEI/EMI/REI, ~28 files total) rather than picking one — versions get bumped, integrations don't get cut by default. Port Jade, Farmer's Delight + its ~22 addon-compat classes (checking each addon mod's own 1.21.1 availability individually), Create/Ponder/Flywheel compat. Handle Alex's Mobs and Prehistoric Fauna as flagged exceptions: confirm with the user whether the unofficial Alex's Mobs NeoForge port (plus its unofficial Citadel dependency) is acceptable before wiring it up, and expect Prehistoric Fauna compat to be dropped outright since no 1.21.1 build appears to exist — reconfirm both at the time, don't rely on this snapshot.

**Phase 10 — Polish.** Lang files, remaining sounds, advancement trees, Dinopedia content authoring, full playtest pass.
