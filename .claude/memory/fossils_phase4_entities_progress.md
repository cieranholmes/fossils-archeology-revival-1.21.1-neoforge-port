## GeckoLib 4.7.2 -> 4.9.2 API drift (verified against actual jars, not guessed — reusable for all remaining entity/animation work)

Package tree `software.bernie.geckolib.core.*` was **eliminated** in 4.9.2 — everything moved up a level:
- `core.animation.*` (Animation, AnimationController, AnimationState, RawAnimation) -> `animation.*`
- `core.animation.keyframe.BoneAnimation`-style -> `animation.keyframe.BoneAnimation`
- `core.animation.state.BoneSnapshot` -> `animation.state.BoneSnapshot`
- `core.object.PlayState` -> `animation.PlayState`
- `core.animatable.instance.AnimatableInstanceCache` -> `animatable.instance.AnimatableInstanceCache`
- `core.molang.MolangParser` -> **removed entirely**, replaced by `loading.math.MathParser`; method `setValue(String, DoubleSupplier)` renamed to `setVariable(String, DoubleSupplier)`
- `CoreGeoBone`/`CoreGeoModel` -> **removed**, replaced by `cache.object.GeoBone` / `model.GeoModel`
- Unchanged: `animatable.GeoEntity`, `util.GeckoLibUtil`, `cache.GeckoLibCache`, `loading.object.BakedAnimations` (all already lacked the `core.` prefix in 4.7.2)
- `AnimationController` public API (constructors, `transitionLength(int)`, `forceAnimationReset()`, `getName()`, `getCurrentAnimation()` -> now returns `AnimationProcessor.QueuedAnimation` (has `.animation()`/`.loopType()`), `adjustTick(double)`, `tickOffset` field, `getAnimationSpeed()`/`setAnimationSpeed(double)`) are all present with matching signatures — safe to port call sites with only import changes.
- `AnimatableManager` now has a **public** `isFirstTick()` getter (didn't exist in 4.7.2) — the source's `AnimatableManagerAccessor` mixin must be deleted, not ported, or it'll generate a duplicate method and crash on mod load.

**The 4 GeckoLib-internals mixins** (not yet ported — needed before any GeoEntity implementing `PrehistoricAnimatable` will actually render/animate correctly):
1. `AnimationControllerMixin` — needs rework: retarget injection from `MolangParser.setValue` to `MathParser.setVariable` (exactly one call site inside `AnimationController.process()`, ~line 519 in 4.9.2 source).
2. `AnimationControllerAccessor` — compatible as-is, just update the package import.
3. `AnimatableManagerAccessor` — **delete**, don't port (see above).
4. `AnimationProcessorMixin` — needs rework, but only type renames (`CoreGeoBone`->`GeoBone`, `CoreGeoModel`->`GeoModel`); injection target (`AnimatableManager.getAnimationControllers()`) unchanged.

**Task #4's core, `Prehistoric.java` itself (1694 source lines) — ported and verified.** This required far more than the previously-mapped GeckoLib/pathfinding drift — MC 1.20.1→1.21.1 reworked huge swaths of the `Entity`/`LivingEntity`/`Mob` API surface that this one file touches almost all of. **This is the most valuable reusable knowledge from this session** — every future entity port (variant subclasses, per-species classes, monster/boss entities) will hit the same points:

- **`defineSynchedData()` is no longer a no-arg method that calls `entityData.define(...)`.** It's now `protected void defineSynchedData(SynchedEntityData.Builder builder)`, abstract-ish (must call `super.defineSynchedData(builder)` and use `builder.define(ACCESSOR, default)` instead of `entityData.define(...)`). `entityData` is no longer freely mutable post-construction from outside this hook.
- **`Entity.dimensions`/`Entity.eyeHeight` fields are now `private`** — no subclass can read or write them directly anymore (a `private access` compile error, not just deprecation). `EntityDimensions` is now a **record** with `width()`/`height()`/`eyeHeight()` **methods**, not public fields — `dimensions.width` style field access breaks, needs `dimensions.width()`.
- **`LivingEntity.getDimensions(Pose)` is now `final`** — cannot be overridden to apply custom age/growth scaling anymore. Instead it internally does `getType().getDimensions().scale(getAgeScale())` — **override `getAgeScale()` instead** (still virtual, no `final`). Since other systems (rider-attachment math, and likely GeckoLib rendering) call `getScale()` and/or `getScale() * getAgeScale()` independently, if a mob's "real" per-instance scale needs to show up in *both* single-hook consumers, override **both** `getScale()` and `getAgeScale()` with the identical computed value via a shared private helper — accept that any vanilla call site combining both multiplicatively (e.g. `getPassengerAttachmentPoint`) will end up squared. This only matters for actually-rideable mobs' default (non-custom-anchor) passenger seat height — a minor, rarely-hit cosmetic edge case, not a functional break.
- **`Entity.refreshDimensions()` is no longer effectively-abstract "roll your own" territory** — vanilla's own base implementation (with a NeoForge `EntityEvent.Size` hook baked in) now already does the "try to grow into a bigger bounding box, fall back gracefully via `fudgePositionAfterSizeChange` if blocked" logic that mods used to have to hand-roll. **Prefer calling `super.refreshDimensions()`** and only add mod-specific side effects on top (e.g. this mod's `MultiPart` hitbox-child dimension propagation) rather than reimplementing the grow/fallback dance. One casualty: the old hand-rolled version could *revert* `dimensions` to the old value and sync a `DIMENSION_VER` tag to force client-side consistency when growth space wasn't found — that specific revert-and-resync trick is **no longer possible** since `dimensions` can't be reassigned from a subclass at all. Dropped this behavior entirely (flagged, not silently lost) — the rare failure-to-grow case may now leave a small client/server dimension mismatch until the next successful growth tick, a minor visual/collision edge case, not a crash or save-corruption risk.
- **Passenger positioning is a different system entirely.** `Entity.getPassengersRidingOffset()` / `Entity.getMyRidingOffset()` **no longer exist at all**. Replaced by a data-driven `EntityAttachments`/`EntityAttachment.PASSENGER` system (`getPassengerAttachmentPoint`/`getVehicleAttachmentPoint`/`getPassengerRidingPosition`). `positionRider(Entity, MoveFunction)` is still a valid override point with the same signature, but its default behavior now computes an absolute final position (not an incremental offset from `getX()/getY()/getZ()`) — call `super.positionRider(passenger, callback)` first and only override with a custom callback invocation when a mod-specific hitbox anchor exists; don't try to reconstruct the old offset formula, vanilla's default is already reasonable.
- **`Mob.maxUpStep()` lost its setter.** `Mob.setMaxUpStep(float)` **no longer exists** — `maxUpStep()` is now purely derived from the `Attributes.STEP_HEIGHT` attribute (default `0.6`), and `LivingEntity.maxUpStep()` *already* special-cases `Math.max(f, 1.0F)` when `getControllingPassenger() instanceof Player`. A mod manually doing "if ridden by player, step-up 1.0, else 0.6" every tick is now **entirely redundant** with vanilla defaults — just delete that code rather than porting it.
- **`Mob.getExperienceReward()` is now `final`**, delegating to `protected int getBaseExperienceReward()` (no params, unlike the old override which had none either — just a rename + the wrapping method is now final and does enchantment-XP-boost processing itself).
- **`AttributeModifier` switched from `UUID`-keyed to `ResourceLocation`-keyed**, and its constructor changed from `(String name, double amount, Operation)` to `(ResourceLocation id, double amount, Operation)` — no more free-text display name, the id **is** the identity now. `AttributeInstance.getModifier`/`removeModifier` take `ResourceLocation`, not `UUID`, correspondingly. Also **`AttributeModifier.Operation.MULTIPLY_BASE` was renamed to `ADD_MULTIPLIED_BASE`** (and by the same pattern, expect `ADD_VALUE`/`ADD_MULTIPLIED_TOTAL` for the other two operations, not their old `ADDITION`/`MULTIPLY_TOTAL`-style names).
- **`TamableAnimal.canBeLeashed()` dropped its `Player` parameter** — now zero-arg, and the base implementation unconditionally returns `true` (no ownership check built in anymore). A mod's old `canBeLeashed(Player player) { return super.canBeLeashed(player) && isOwnedBy(player); }` override has no direct replacement hook; this port **dropped the override entirely** (inherits unconditional `true`), meaning **non-owners can now leash a tamed dino** — a real, deliberate behavior regression versus 1.20.1, not yet worth fixing given no obvious replacement hook was found. Revisit if a look at how vanilla's own leash-item-use code checks ownership elsewhere turns up a hook.
- **`TamableAnimal.reassessTameGoals()` was removed entirely** (no such method anywhere in 1.21.1 sources) — it had no vanilla call site calling into it anymore either. Its one usage in this mod (reset order to WANDER when untamed via betrayal) was inlined directly at the `setTame(false, ...)` call site in `hurt()` instead of relying on an override hook.
- **Entity spawn data**: Architectury's `EntitySpawnExtension` (and its `getAddEntityPacket()` override calling `NetworkManager.createAddEntityPacket`) is dropped along with Architectury itself. NeoForge's native equivalent is `net.neoforged.neoforge.entity.IEntityWithComplexSpawn`, with methods renamed `writeSpawnData(RegistryFriendlyByteBuf)`/`readSpawnData(RegistryFriendlyByteBuf)` (note: `RegistryFriendlyByteBuf`, not plain `FriendlyByteBuf`). **No `getAddEntityPacket()` override is needed at all** — NeoForge automatically wraps an `AdvancedAddEntityPayload` around any `IEntityWithComplexSpawn` entity's normal spawn packet and calls `writeSpawnData`/`readSpawnData` transparently. This also let this port drop a whole Fabric-timing-bug workaround (`Platform.isFabric()`/`synTime`/a mixin-injected `fossilsArcheologyRevival$markNonDefaultAsDirty()` duck-interface call) that only existed to paper over an Architectury+Fabric-specific race condition, irrelevant on NeoForge.
- **`EntityDataAccessor` fields for built-in synced data (`DATA_CUSTOM_NAME` etc.) are `private` in `Entity`**, so `onSyncedDataUpdated(EntityDataAccessor<?> key)` can no longer do `DATA_CUSTOM_NAME.equals(key)` from a subclass. Where a mod needs to react to a built-in field changing (e.g. re-checking name-tag-based variant conditions whenever the custom name changes), **override the corresponding public setter instead** (e.g. `setCustomName(Component)`) rather than key-comparing in `onSyncedDataUpdated`.
- **`ServerAdvancementManager.getAdvancement(ResourceLocation)` was renamed to `.get(ResourceLocation)`**, and now returns `AdvancementHolder` instead of the bare `Advancement` class (import `net.minecraft.advancements.AdvancementHolder`).
- **`Level.threadSafeRandom` is now `private`** (was a package-visible-ish field before) — no public accessor was found; fell back to the plain public `Level.random` field for a one-off seeded-sound-packet construction (loses the "safe to call off the main thread" property, but the call site here is normal main-thread server game logic anyway, so it's a safe substitution).
- Confirmed **unchanged** despite initial suspicion (verified directly against decompiled source before changing, catching two of my own wrong assumptions in the process): `Mob.customServerAiStep()` is still zero-arg; `InteractionResult.sidedSuccess(boolean)` still exists (didn't get removed in the `InteractionResult` enum rework); `Mob.doHurtTarget(Entity)` and `Entity.killedEntity(ServerLevel, LivingEntity)` and `Entity.causeFallDamage(float, float, DamageSource)` and `Entity.getFluidJumpThreshold()` are all unchanged; `AgeableMob.getBreedOffspring(ServerLevel, AgeableMob)` unchanged; `Mob.finalizeSpawn` dropped its `@Nullable CompoundTag dataTag` 5th parameter (now 4-arg) — the mod's use of that param to pick an `NbtCondition`-based variant on spawn was dropped along with it (flagged, no replacement hook found yet).

**New drift found in this final stretch** (add to the running list above for reuse in tasks #6-#9):
- **`LivingEntity.canBreatheUnderwater()` is now `final`**, deprecated in favor of NeoForge's `ILivingEntityExtension.canDrownInFluidType(FluidType type)` (packages: `net.neoforged.neoforge.fluids.FluidType`, `net.neoforged.neoforge.common.NeoForgeMod` for `NeoForgeMod.WATER_TYPE.value()`). A mod that used to do `canBreatheUnderwater() { return true; }` should instead override `canDrownInFluidType(FluidType type) { return type != NeoForgeMod.WATER_TYPE.value() && super.canDrownInFluidType(type); }`.
- **`MobType` (the old `MobType.WATER`/`Mob.getMobType()` pair) was removed from vanilla entirely** — no replacement hook found; any override returning `MobType.WATER` etc. should just be dropped (nothing calls `getMobType()` anymore).
- **`Entity.getMyRidingOffset()` (a *passenger*-side seat-offset override) is gone**, replaced by `Entity.getVehicleAttachmentPoint(Entity vehicle)` returning a full `Vec3` (not just a Y double) computed from the `EntityAttachments`/`EntityAttachment.VEHICLE` system. Override that instead, e.g. `super.getVehicleAttachmentPoint(vehicle).add(0, yOffset, 0)`.
- **`MoveControl.Operation` (the nested `WAIT`/`MOVE_TO`/`STRAFE`/`JUMPING` enum) is `protected`**, so any class that isn't itself a `MoveControl` subclass cannot reference `Operation.MOVE_TO` etc. directly even via import (Java visibility, not just a lint issue — real compile error "has protected access"). Fix pattern: add no-arg convenience wrapper methods (`setOperationMoveTo()`/`setOperationWait()`) on the actual `MoveControl` subclass (which *can* see `Operation`), and have unrelated classes call those instead of touching the enum. Applied this to `CustomFlightMoveControl` for `PrehistoricFlying`'s benefit — check for the same pattern anywhere else a non-`MoveControl` class tries to drive a custom move control's operation state directly.
- **`ItemStack.getOrCreateTag()` no longer exists at all** — full Data Components migration. ### Reusable pattern: parallel Agent-tool delegation for bulk entity porting

This is the single most valuable technique from this session, worth reusing for Phase 2 (Items), Phase 5 (Client assets/datagen), Phase 6 (Worldgen), Phase 7 (Datagen) — any phase with many structurally-similar independent files to port:

1. **Batch by independence, not by theme.** Split N files that don't share write-targets into groups of 5-8 and launch one background `Agent` per group (`subagent_type: general-purpose`), running them all in parallel in a single message. Land dinosaurs (36 files) went out as 6 batches of 6; swimming/fish/flying got their own batches; monster mobs, ai/anu, loose entities, and finally renderers+models all got the same treatment.
2. **Every agent prompt must contain the FULL known-API-drift catalog** (not a summary/link) — copy the relevant bullet points from this memory file directly into the prompt. Agents have no access to this memory system.
3. **Explicit boundary: "do NOT touch shared files"** (`ModEntities.java`, `ClientModEvents.java`, `ModItems.java`) — those are reserved for the orchestrating session to edit serially after all parallel batches land, avoiding merge races on files every batch would otherwise want to touch.
4. **Explicit permission for forward references**: "if you reference a class another agent is porting concurrently, that's fine, don't stub around it" — this matters because e.g. land-dino agents reference `entity/ai/*` goal classes and other not-yet-landed species classes constantly; without this instruction agents waste time inventing placeholder types.
5. **Agents do NOT run `./gradlew`** — compilation is checked centrally once, after all parallel batches land, by the orchestrating session. Running gradle from N parallel agents would race on the build lock/daemon.
6. Aggregate compile errors after all batches land are almost always: (a) a handful of genuinely novel API-drift points no single agent's prompt anticipated, (b) missing registrations in the shared files the orchestrator hasn't added yet, (c) 1-2 agents guessing wrong on an ambiguous signature. All three are fast to fix centrally with 1-2 `./gradlew compileJava` iterations — cheaper than trying to make every agent prompt exhaustive up front.
7. Agents are generally excellent at flagging (not silently guessing at) missing dependencies — e.g. correctly detecting `ModItems.MAGIC_CONCH`/`ModParticles`/`ModDimensions` don't exist yet and leaving a clear TODO/flag rather than inventing those systems. Trust their flags; verify them centrally rather than re-deriving from scratch.

### New MC 1.20.1→1.21.1 API drift discovered this session (append to the running catalog — verified against decompiled sources, not guessed)

Entity/gameplay API:
- **`LivingEntity.getDimensions(Pose pose)` (final) is `pose == Pose.SLEEPING ? SLEEPING_DIMENSIONS : getDefaultDimensions(pose).scale(getScale())`** — confirmed by reading the actual source. This means: a species overriding sleeping-pose dimensions specifically has **no override point at all** (hardcoded 0.2×0.2, must be dropped/flagged, unfixable). But a species overriding dimensions for any OTHER pose (e.g. `Pose.FALL_FLYING` for a gliding species) **can** still do it by overriding the still-virtual `protected EntityDimensions getDefaultDimensions(Pose pose)` instead. Don't conflate these two cases — check which pose the source override actually guards on before deciding it's unfixable.
- **`Entity.canChangeDimensions()` (0-arg) → `canChangeDimensions(Level oldLevel, Level newLevel)`** (2-arg).
- **`Entity.setSecondsOnFire(int)` → `igniteForSeconds(float)`** (also note the underlying storage is now tick-based via `igniteForTicks(int)`, `igniteForSeconds` just does `Mth.floor(seconds*20)`).
- **`DamageSource.isIndirect()` removed entirely** — no direct replacement method; reconstruct as `source.getDirectEntity() != source.getEntity()`.
- **`FollowOwnerGoal` constructor is now `(TamableAnimal, double speedModifier, float startDistance, float stopDistance)`** — 4-arg, the old 5-arg version with a trailing `canFly`-style boolean is gone; just drop the boolean argument.
- **`LargeFireball` constructor is now `(Level, LivingEntity, Vec3 direction, int explosionPower)`** — takes a `Vec3` for the direction vector instead of 3 separate `double x,y,z` args; wrap `new Vec3(x,y,z)` at the call site.
- **`SavedData.save(CompoundTag)` → `save(CompoundTag, HolderLookup.Provider)`** (2-arg now). **`SavedData.Factory<T>` is a record** `(Supplier<T> constructor, BiFunction<CompoundTag, HolderLookup.Provider, T> deserializer, @Nullable DataFixTypes type)` with a convenience 2-arg constructor dropping the `DataFixTypes` — **a bare method reference like `MyData::load` no longer satisfies `DimensionDataStorage.get(...)`**; wrap it: `new SavedData.Factory<>(MyData::new, (tag, provider) -> MyData.load(tag))`.
- **`LivingEntity.getCurrentSwingDuration()` and `jumpFromGround()` are now `public`** (were `protected`) — an override in a mod class that still declares them `protected` fails to compile ("attempting to assign weaker access privileges"); just widen the override to `public`.
- **`Animal.isFood(ItemStack)` is now abstract** — every `Animal`/`TamableAnimal` subclass must implement it even if the species has no food/breeding interaction; `return false;` is a safe, behavior-preserving default when the source had no equivalent logic.

- **`Model.renderToBuffer(...)` and `ModelPart.render(...)` both collapsed their trailing `float red, green, blue, alpha` params into a single packed `int color`** — exactly the same collapse pattern already known for GeckoLib's `GeoRenderer.preRender`. Fix: change the override signature to take one `int color` and pass it straight through; for a call site that used to pass literal `1,1,1,1` (opaque white), pass `-1` (0xFFFFFFFF); to preserve a computed alpha, use `FastColor.ARGB32.colorFromFloat(alpha, red, green, blue)`.
- **`LivingEntityRenderer.setupRotations(...)` gained a trailing `float nativeScale` parameter** — same drift shape as GeckoLib's `applyRotations` 5-arg→6-arg change already catalogued; override the new signature and forward the extra param (or ignore it) as needed.

New style: `addVertex(matrix4f,x,y,z).setColor(r,g,b,a).setUv(u,v).setOverlay(o).setLight(l).setNormal(nx,ny,nz)` — note `setNormal` takes **already-transformed** raw floats, not a `Matrix3f` — if the old code relied on the vertex builder to apply the normal-matrix transform, you must do it manually first: `Vector3f n = new Vector3f(nx,ny,nz); matrix3f.transform(n);` then pass `n.x(), n.y(), n.z()` to `setNormal`.
