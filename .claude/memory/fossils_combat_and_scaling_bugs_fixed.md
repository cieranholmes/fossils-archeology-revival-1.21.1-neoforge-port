Found via the user actually playing the game post-Phase-4 (spawning a Tyrannosaurus + pig) and reporting "it chases but never hits" and "the dinosaurs are the wrong size compared to 1.20.1". Both turned out to be real, previously-undetected bugs (Phase 4's own verification only checked spawning/NBT population, never actual combat or visual size) - not the same bug, four independent root causes. All four fixes are in `entity/ai/DelayedAttackGoal.java`, `entity/prehistoric/base/Prehistoric.java`, `client/renderer/entity/PrehistoricGeoRenderer.java`, `client/renderer/entity/PrehistoricFishGeoRenderer.java`.

## Bug #1: `DelayedAttackGoal` never dealt damage for "heavy" (attack-box) animations

The 1.20.1 source's `checkAndPerformAttack` had `if (animationInfo.usesAttackBox && enemy instanceof ServerPlayer player) { ...sync to client...; doingHeavyAttack = true; }` — the attack-box/client-hitbox-reporting path was **only** for player targets. When this was ported in an earlier session, the `enemy instanceof ServerPlayer` half of the condition was dropped, leaving just `if (animationInfo.usesAttackBox)`. Result: **any species whose attack animation has `"uses_attack_box": true` in its animation JSON never deals damage to anything at all** (not just players) — it sets `doingHeavyAttack = true` and waits for a networked attack-box hit confirmation that Phase 3 (networking) never built, and the plain `attackDamageTick` timer path is never reached. Fix: restored the `enemy instanceof ServerPlayer` condition, so every non-player target always falls through to the simple actionDelay-based damage timer regardless of `usesAttackBox`. (Tyrannosaurus's own animation.json happens not to use `uses_attack_box` at all, so this specific bug wasn't why the T-Rex/pig case failed — but it's a real, confirmed-fixed bug that would affect whichever species do use it.)

## Bug #2: `getAgeScale()` duplicating `getScale()` squared the entity's effective size for hitbox/eye-height

This is the single most important thing to remember for any future Prehistoric-hierarchy work. In 1.20.1, `Prehistoric.getDimensions(Pose)` was a normal override: `return getType().getDimensions().scale(getScale())` — one multiplication, using `getScale()` alone (source has no `getAgeScale()` override at all). In 1.21.1, `LivingEntity.getDimensions(Pose)` became `final`, forcing the port (in an earlier Phase 4 session) to instead override the still-virtual `getDefaultDimensions(Pose)` hook — except vanilla's `LivingEntity.getDefaultDimensions()` itself does `getType().getDimensions().scale(getAgeScale())`, and the outer final `getDimensions()` wrapper *also* multiplies by `getScale()` on top: effectively `scale(getAgeScale()).scale(getScale())`. Since `Prehistoric` had both `getScale()` and `getAgeScale()` overridden to return the identical `computeScale()` value (to satisfy two different vanilla call sites independently), every dimension/eye-height computation applied the growth scale **twice** (squared). Confirmed by measurement: adult Tyrannosaurus (`computeScale()` = 2.6) had an eye height of 7.18 blocks instead of the correct 2.76 — steep enough that `HuntingTargetGoal`'s line-of-sight raycast to any ground-level prey clipped through terrain almost every time, so it could never lock onto a target at all. Same squaring silently affected `LivingEntity.getPassengerAttachmentPoint()`'s `getScale() * getAgeScale()` product (a "minor cosmetic" issue previously noted in [[fossils-phase4-entities-progress]] before this session traced it to the same root cause).

**Fix:** `getAgeScale()` now returns a neutral `1` unconditionally; `getScale()` alone still returns `computeScale()` and remains the sole carrier of the real value everywhere it matters. Verified via decompiled source that no other vanilla call site reads `getAgeScale()` in isolation expecting the full growth value — every use is paired multiplicatively with `getScale()`, so neutralizing it is safe. This is the correct general pattern any time 1.21.1's `getScale()`/`getAgeScale()` split needs to collapse back to a single "total scale" value the mod's own design assumes.

## Bug #3: `more-hitboxes`' own `EntityMixin` refresh of `getAttackBounds()` never fires in this environment

`DelayedAttackGoal.isInRange()` → `Util.canReachPrey()` checks `prehistoric.getEntityHitboxData().getAttackBounds().intersects(target.getBoundingBox())`. `getAttackBounds()` is a **cached** AABB (the library's own doc: "Returns... a cached version") that's supposed to auto-refresh via `more-hitboxes`' bundled `EntityMixin` (`@Inject(method = "setBoundingBox", at = @At("RETURN"))` calling `makeAttackBounds()`), which fires whenever vanilla's own position/dimension-update machinery calls `Entity.setBoundingBox(...)`. Confirmed live via debug logging: the cached box stayed **permanently frozen at its construction-time value** (anchored near world origin, since `EntityHitboxDataFactory.create(this)` runs in a field initializer before the entity has any real position) even as the entity visibly moved across the map — meaning the mixin never actually applies. `morehitboxes.mixins.json` declares `"compatibilityLevel": "JAVA_21"`; the server log independently shows GeckoLib's own `common.LivingEntityMixin` failing to apply with `"Class version 65 required is higher than the class version supported by the current version of Mixin (JAVA_17 supports class version 61)"` — strongly suggesting the bundled Mixin transformer in this NeoForge setup only supports up to Java 17 bytecode, silently dropping any mod's `JAVA_21`-declared mixins (including all of `more-hitboxes`', not just this one). **This is a likely systemic gap, not a one-off** — flag it if any other `more-hitboxes` or GeckoLib mixin-dependent behavior (multi-part hitbox damage routing, anything else relying on `EntityMixin`/`MobMixin`/GeckoLib's `LivingEntityMixin`) seems inert or stuck; the same root cause is the first thing to check.

**Fix applied here:** added an explicit `hitboxData.makeAttackBounds();` call inside `Prehistoric.aiStep()` (runs every tick, both sides) to manually refresh the box, working around the broken mixin without touching the library itself. **Not fixed / still open:** the underlying Mixin-compatibility-level problem itself — if other more-hitboxes-mixin-dependent behavior is ever found broken, this same manual-refresh-from-mod-code workaround pattern is the fix, not trying to repair the mixin loading.

## Bug #4: GeckoLib's own automatic entity scaling duplicated our explicit `withScale()` call (the actual visual-size bug)

This was the real cause of "Tyrannosaurus/Brachiosaurus look huge, Velociraptor looks tiny" — and it's **entirely separate from bug #2** (which only affected hitbox/collision/eye-height, not rendering). `GeoEntityRenderer.render()` (GeckoLib **library** code, not ours) unconditionally does `float nativeScale = livingEntity.getScale(); poseStack.scale(nativeScale, nativeScale, nativeScale);` for any `LivingEntity` — a built-in, automatic feature every GeckoLib mod gets for free. But `PrehistoricGeoRenderer.preRender()` (and `PrehistoricFishGeoRenderer.preRender()`) **also** explicitly called `withScale(animatable.getScale())`, which independently sets `scaleWidth`/`scaleHeight` fields applied via `scaleModelForRender()` earlier in the same render pass. Both scale calls hit the same `PoseStack` cumulatively: `getScale()` applied twice = squared (2.6² = 6.76 for Tyrannosaurus, 0.6² = 0.36 for Velociraptor) — matching the reported "some bigger, some smaller" pattern exactly, and independently reproducing almost exactly the user's "roughly 10 blocks tall" observation (1.25 base height × 6.76 ≈ 8.45).

**Fix:** removed the redundant `withScale(animatable.getScale())` call (and the now-empty `preRender()` override) from both renderer classes entirely — GeckoLib's own automatic `nativeScale` mechanism handles it alone. Confirmed via `grep -rn "withScale"` that no other renderer in the codebase has the same redundant call. **General rule for any future GeckoLib renderer work in this mod:** never call `withScale()`/`scaleModelForRender()` with the entity's own `getScale()` value for a plain `LivingEntity`-based `GeoEntityRenderer` subclass — GeckoLib already does this automatically. `withScale()` is only for a genuinely *additional* multiplier on top of vanilla scale (which this mod doesn't need). `PrehistoricSkeleton`'s renderer is a legitimate exception: it extends `Entity` directly (not `LivingEntity`), so it does *not* get GeckoLib's automatic nativeScale treatment and correctly must call `scaleModelForRender(getScale(), getScale(), ...)` itself — don't "fix" that one.

## Reusable debugging technique that cracked this (worth reusing for any future gameplay-logic bug)

Static code reading alone stalled repeatedly on both bugs #2-#4 (formulas checked out identical to source multiple times over). What actually worked: **temporary `System.out.println` debug prints inserted directly into the suspect goal/renderer methods**, rebuild (`./gradlew compileJava`), reboot a dedicated test server (`./gradlew runServer --console=plain` in background, per the RCON approach in [[fossils-phase4-entities-progress]]), reproduce live via RCON, then `grep` the resulting log for the debug tag. This was iterated ~6 times, each time narrowing the search (goal-level canUse/target → line-of-sight specifically → the `more-hitboxes` attack-bounds cache → finally the client-side render path once the user confirmed hitbox/server math was provably correct but the visual bug persisted). **Always remove the debug prints and restore clean code once the bug is found** - every round of this was cleaned up immediately after diagnosis, never left in committed code. Also: `./gradlew --stop` (kill the Gradle daemon) + `./gradlew clean compileJava` is worth doing once early if a reported bug seems to persist "impossibly" after a source fix — rules out stale-build confusion before spending more effort on the actual logic.

**Gotcha hit repeatedly during this session's RCON testing (not a mod bug, a test-harness one):** a freshly booted dedicated server needs `/forceload add <x1> <z1> <x2> <z2>` before any spawned entity's AI/goal-selector will tick at all - without it, an entity looks completely "frozen" (no movement, no debug output firing) purely because the chunk isn't in the game's "entity ticking" distance range with zero players connected. This produced several false alarms mid-investigation before being identified; always `/forceload` first when testing entity behavior via a headless dedicated server with no player joined.
