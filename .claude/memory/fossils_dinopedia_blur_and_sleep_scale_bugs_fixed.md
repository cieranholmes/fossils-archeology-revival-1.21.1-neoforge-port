Found via live user testing (not a migration-phase task) after all 10 phases were already complete - see [[project-neoforge-port]]. Both bugs lived in `DinopediaScreen.java`'s live-entity-preview rendering (`renderEntityInDinopedia`) and its `render()`/`renderBackground()` split, and both existed unnoticed in the 1.20.1 source mod too (same code, carried over faithfully by the port) - they only became *visible* because of real API/behavior drift in vanilla between 1.20.1 and 1.21.1.

## Bug 1: sleeping dinosaur's preview model becomes huge

`renderEntityInDinopedia` computed the preview's render scale as `(int) (35 / entity.getBbWidth())` for any `Prehistoric`. Vanilla's `LivingEntity.getDimensions(Pose)` is `final` and special-cases `Pose.SLEEPING` to return a tiny hardcoded `SLEEPING_DIMENSIONS` constant, **completely ignoring the entity's actual scaled size** - so a sleeping dinosaur's `getBbWidth()` suddenly reports near-zero, and `35 / nearZero` blows the scale up massively.

**Fix**: query `entity.getDimensions(Pose.STANDING)` explicitly instead of `getBbWidth()`/`getPose()` - passing the pose parameter explicitly bypasses the `SLEEPING` special case entirely and always returns the real scaled size.

## Bug 2: live entity preview + book background render blurry

This took much longer to find; two false leads before the real cause:
- Ruled out: mipmapping (doesn't apply to entity/GUI textures - always 0 mip levels regardless of the video-settings "Mipmap Levels" slider, which only governs the block atlas), texture `blur`/`clamp` metadata (no `.mcmeta` exists for `dinopedia.png`/`dinopedia_mood.png`, confirmed both nearest-filtered; the background PNG's page area is also confirmed fully opaque, alpha=255, via direct pixel sampling - not a translucency-bleed issue), shaders (user confirmed vanilla-only), GUI Scale (user confirmed no change fixed/integer vs Auto), and the GUI's 3D-in-GUI ortho depth range (confirmed ~10000-unit headroom via `GameRenderer`'s `setOrtho(...,1000,21000)` + a `(0,0,-11000)` modelview baseline - nowhere near being clipped).
- False lead (still fixed, but wasn't the main cause): GeckoLib's `GeoEntityRenderer` derives the head bone's tracking yaw from `(lerp(yHeadRotO,yHeadRot) - lerp(yBodyRotO,yBodyRot))` clamped to ±85°. `renderEntityInDinopedia` pins `yBodyRot` to a fixed angle for the preview but never touched `yHeadRot`/`yHeadRotO`, which keep reading the *live* entity's real, still-changing head rotation (it keeps ticking/looking around in the world while the screen is open) - a real bug causing head/neck jitter, fixed by also pinning `yHeadRot`/`yHeadRotO` to the same forced angle (matching what vanilla's own `InventoryScreen.renderEntityInInventoryFollowsMouse` does). Confirmed via a zoomed crop of a user screenshot that the visible defect was actually uniform Gaussian-style softness, not directional smearing - ruling out an animation/rotation-driven artifact, since it affected non-animated egg/Quagga previews too.
- **Real cause**: `DinopediaScreen.render()` called `renderBackground(guiGraphics, mouseX, mouseY, partialTick)` explicitly, then called `super.render(...)`. Vanilla's base `Screen.render()` (1.21.1) *also* calls `this.renderBackground(...)` internally as its first line - a real behavior added after 1.20.1 as part of vanilla's "menu background blur" feature (`Screen.renderBlurredBackground()` → `GameRenderer.processBlurEffect()`, a real per-frame GPU Gaussian blur pass over the main render target's current contents). So `renderBackground()` ran twice per frame: once explicitly (which drew the book texture + live entity on top of the blurred world, correctly crisp at that point), then again via `super.render()` - and that *second* call's blur pass hit the main render target's *current* contents, which by then included the freshly-drawn book texture + entity, blurring both. Anything drawn afterward (buttons via `super.render()`'s widget loop, then text/food-icons in `renderForegroundLayer`) was never touched by a further blur pass, hence stayed crisp - matching every symptom reported (background + entity blurry, text/items sharp, present for all entity types including non-animated ones).

**Fix**: moved the book-texture-blit + entity-render call out of a separate `renderBackgroundLayer()` invoked before `super.render()`, into an override of `renderBackground(GuiGraphics, int, int, float)` that calls `super.renderBackground(...)` first, then draws the book+entity. `render()` now just calls `super.render(...)` once (which invokes the override exactly once) followed by the foreground/text layer. This preserves the original draw order but guarantees the blur pass never runs a second time after our content is drawn.

## Reusable insight

Any Screen subclass that explicitly calls `renderBackground(...)` *and* separately calls `super.render(...)` in the same frame double-runs vanilla's per-frame GUI blur post-effect in 1.21.1+ (this didn't exist as a `Screen.render()`-embedded call in 1.20.1) - check for this exact double-call pattern first if a ported custom `Screen` shows background/foreground-drawn-before-`super.render()` content looking soft/blurry while content drawn after `super.render()` stays crisp. This is a real, silent, decompile-confirmed source of "upstream code that used to be fine now produces a visible bug purely from vanilla API/behavior drift, not from anything the port changed" - same category as [[fossils-known-upstream-bugs]] but only surfaces from actual live-user testing, not code review, since it's a purely visual artifact.
