During a code-review pass on Phase 4 tasks #1-3 ([[fossils-phase4-entities-progress]]), 8 findings surfaced. Each was individually checked against the 1.20.1 source and confirmed to be a byte-for-byte match of existing source logic — i.e. real bugs, but inherited from upstream, not introduced by this port. **User's explicit call (2026-08-12): leave these as-is for now, just track them in memory** — not fixing during the port itself, to preserve upstream parity/avoid unplanned scope creep mid-migration.

**Why kept:** so a future session (this one's or a fresh Phase 8/cleanup pass) has a ready-made punch list instead of rediscovering these from scratch. **How to apply:** when Phase 8 ("Mixin cleanup pass") or any dedicated bug-fix pass is reached, revisit this list and ask the user whether to fix each one now that porting is further along. Don't fix opportunistically while touching these files for unrelated reasons unless asked — these are deliberately deferred, not forgotten.

1. **`entity/ai/navigation/PrehistoricPathNavigation.java`, `moveTo(Entity, double)`** — returns `true` even when `createPath` found no path (only sets `speedModifier` in that branch). Callers relying on the boolean to detect pathing failure won't.
2. **`entity/ai/control/CustomFlightMoveControl.java`, `tick()`** — the final `else` branch (`isFlying()==true` but `operation != MOVE_TO`) calls `mob.setNoGravity(false)`. A flying mob that reaches an air waypoint without landing (the `!shouldLandAtTarget` path sets `operation = WAIT` without `mob.setFlying(false)`) starts free-falling on the very next tick while `isFlying()` still reports `true`.
3. **`entity/ai/navigation/PrehistoricWallClimberNavigation.java`, `tick()`** — the `width <= 1` branch compares squared distance (`distToCenterSqr`) against a non-squared threshold (`width * 2`), unlike the `width > 1` branch which correctly uses `closerToCenterThan`. Small mobs treat the wall-climb target as "reached" while still ~1 block away.
4. **`entity/prehistoric/system/LeapSystem.java`, `stopLeap()`** — clears the entity leap `target` but never clears `blockTarget`, despite the Javadoc claiming to remove "the leap target". A force-stopped block-leap can silently re-trigger on the very next `serverTick()`.
5. **`entity/prehistoric/system/MeganeuraAttachSystem.java`** — `tryTicks` only increments once already `> 0`, but it's only set non-zero by `approachAttachPos()`, which itself only runs once the mob is already within `dist < 1` of the target. The `MAX_TRY_TICKS` timeout never fires for a genuinely unreachable attach target — the mob keeps trying indefinitely instead of giving up after ~15s.
6. **`entity/ai/control/CustomFlightMoveControl.java`** — vertical velocity (`targetYMove`) is computed from the raw, un-smoothed `targetPitch`, while horizontal velocity and the actually-applied rotation use the smoothed `newPitch`/`newYaw`. Produces visibly jerky vertical motion during sharp altitude changes.
7. **`entity/prehistoric/system/LeapSystem.java`, `serverTick()`** — unchecked cast `(LivingEntity) mob.getVehicle()` can throw `ClassCastException` if the ridden entity isn't a `LivingEntity` (plausible since `tryAttackRiding(Entity target)` accepts any `Entity`, not just `LivingEntity`).
8. **`entity/prehistoric/system/FlyingSleepSystem.java`** — the deferred landing-approach branch (triggered when `nextTryTick == currentTick`) calls `trySleepingOrLanding()` without re-checking `canSleep()`/`wantsToSleep()`, unlike the initial trigger which gates on both. A mob can end up asleep despite having gained a target/taken damage/gone hungry during the scheduled-wait window.
9. **`entity/prehistoric/base/DinosaurEgg.java`, `readAdditionalSaveData()`** — calls `PrehistoricEntityInfo.valueOf(compound.getString("PrehistoricEntityInfo"))` with no existence check or fallback. `CompoundTag.getString` returns `""` for a missing key, so `IllegalArgumentException` is thrown whenever the entity is loaded/summoned with NBT that lacks the tag (confirmed live: `/summon fossils:dinosaur_egg` fails with "Unable to summon entity" during the Tyrannosaurus vertical-slice test on 2026-08-12). Normal gameplay paths (`hatchEgg`/`procreate`) always set the field explicitly before adding the entity to the world, so this only bites raw `/summon`/malformed-NBT cases — not blocking, but a real crash-on-bad-input bug inherited from upstream.
10. **`entity/prehistoric/Postosuchus.java`'s animation JSON**, `animation.postosuchus.run` — one MoLang expression is malformed: `"math.cos(query.anim_time*360/0.5+)*-2"` (dangling `+` with nothing after it, in the `Y` component of one bone's rotation vector). Confirmed byte-for-byte identical in the 1.20.1 source's `postosuchus.animation.json` — a genuine upstream animation-authoring typo, not a porting artifact. GeckoLib logs `Unable to parse animation: animation.postosuchus.run` / `Failed to parse expression` on every client boot once Postosuchus's assets are loaded (confirmed live during the 2026-08-12 task #7 species-batch verification), but does not crash — the animation controller just silently fails to apply that one rotation component.
11. **`entity/PrehistoricSkeleton.java`, `readAdditionalSaveData()` -> `setInfoType()` -> `info()`** — same root cause as bug #9: calls `PrehistoricEntityInfo.valueOf(...)` with no fallback for a missing/empty NBT string, throwing `IllegalArgumentException`. Confirmed live: `/summon fossils:skeleton` fails with "Unable to summon entity" during the 2026-08-12 task #7 monster/loose-entity verification. Same non-blocking scope as bug #9 (only raw `/summon`/malformed-NBT paths, not normal gameplay via `FossilItem`-spawned skeletons which always set the field first).
