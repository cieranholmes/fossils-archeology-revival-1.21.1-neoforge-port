## Addon compile fixes (task 10's ported files vs. the real resolved jars)

Nearly every addon needed SOME fix once checked against the actual jar via `javap`/`unzip -l` (method: extract the class from `~/.gradle/caches/modules-2/files-2.1/...`, `javap -p` it, compare field names):

- **Simple package/class renames** (fields unchanged): `AlexDelightCompat` (`item.ModItems`→`registry.ADItems`), `FarmerRespiteCompat` (`umpaz.farmersrespite.common.registry`→`com.farmersrespite.core.registry`), `ExpandedDelightCompat` (`com.ianm1647.expandeddelight.registry.{Item,Block}Registry`→`ianm1647.expandeddelight.common.registry.ED{Items,Blocks}`, plus one real rename: `RAW_CINNAMON`/`GROUND_CINNAMON`→`CINNAMON_STICK`/`CINNAMON`), `CoffeeDelightCompat` (`club.someoneice.cofe_delight.init.ItemInit`→`lcyzsdh.coffee_delight.registry.ItemRegistry`, full rebrand but fields unchanged), `CasualnessDelightCompat` (`com.va11halla.casualness_delight.registry.ItemRegistry`→`top.tobitobi.casualnessdelight.common.registry.ModItems`, fields PascalCase→SCREAMING_SNAKE_CASE; 3 items - `RawFriedDumpling`/`FriedDumpling`/`BowlOfFriedDumpling` - genuinely no longer exist in v0.6, dropped with a comment), `ButcherDelightFoodCompat` (`net.mcreator.butchersdelightfoods`→`net.mcreator.butchersdelight`, dropped "foods" suffix; `REGISTRY.getEntries()` loop shape unchanged), `EndDelightCompat` (`registry.{Item,Block}Registry`→`registry.Mod{Items,Blocks}`, all 33 fields PascalCase→SNAKE_CASE, `ChorusFruitPieBlock` confirmed still extends FD's own `PieBlock`), `EnderDelightCompat` (`block.{ModBlocks,PieBlock}`/`item.ModItems`→`Common.Registries.{EdBlocks,EdItems}` - note unusual capitalized package segments; source's own addon-specific `PieBlock` class no longer exists at all, the addon now reuses FD's `PieBlock` directly).
- **Field-type change, not a rename**: `BrewinAndChewinCompat` - `BnCItems` fields are now plain `Item` (not `Supplier<Item>`/`DeferredHolder`), so all `.get()` calls had to be dropped.
- **Missing transitive dependency of the addon itself, not a code bug**: `CornDelightCompat` - `ItemRegistry`'s `DeferredItem<cn.mcmod_mmf.mmlib.item.ItemFoodBase>` generic type needs "Mysterious Mountain Lib" (`mmlib`) on the classpath even though this file never references it by name (javac needs the full type resolvable). Added `mmlib:1.1.8-1.21.1` as its own compileOnly+runtimeOnly dependency.
- **Modrinth version_number ambiguity, not a code bug at all**: `FestiveDelightCompat` and `SeedDelightCompat` both needed zero code changes - the actual bug was in `gradle.properties`. Both projects reuse the SAME version_number string (`"2.0.0"`, `"1.0.1"`) across multiple **different loader/game-version builds**, and resolving by plain version_number silently picked a genuine Forge (or older-MC) jar whose `net.minecraftforge.registries.RegistryObject` doesn't exist on a NeoForge classpath (`cannot access RegistryObject` errors). Fixed by pinning to the specific Modrinth **version ID** instead of the version_number (`festive_delight_version=FP8ZwEus`, `seed_delight_version=uzv8gBFo`) - **this is a real, generalizable gotcha**: never trust a Modrinth version_number alone when a project has multiple loader tags on the same number; always cross-check the `loaders`/`game_versions` fields via the version-list API endpoint.
- **Full rebrand with almost no field overlap, required a judgment call**: `ArgentinaDelightCompat` - "Argentina's Delight" (source, package `net.mcreator.cambiandoversion`) has no 1.21.1 build; the only NeoForge 1.21.1 build is a genuinely different MCreator project "Argentina's Delight Reborn" (`net.mcreator.argentinasdelightreborn`, modid `argentinasdelightreborn`, confirmed via its own neoforge.mods.toml) with a ~44-field roster sharing almost no names with source's 67 Spanish-named items. Rather than force a fake 1:1 mapping, ported a conservative 14-item subset of confidently-identifiable finished dishes (`BEEF_RIBS`/`VACIO`/`ENTRECOTE`/`MARDELPLATASTEAK`/`SKEWERITEM`/`HALFPORK`/`PORKLOINSLICE`/`PORKLOINITEM`/`PORKRIBSITEM`/`PORKLEGSLICE`/`CHITTERLINGS`/`CHORIZO`/`CHORIPAN`/`CHORIZOS`), explicitly excluding intermediate cooking-state blocks (`*_ONBOARD`/`*_ONGRILL`), tools (`FACON` knife, `BULLHORN`), and guide books. Documented in-file as a conservative best-effort mapping, not a verified 1:1 port - flag for re-audit if precise fidelity to this specific addon's food list ever matters.

## Real runtime bug found via live `runServer` boot (not catchable by compile or datagen)

`CulturalDelightCompat.registerFoodMappings()` crashed `FMLCommonSetupEvent` dispatch with `ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0` at `ImmutableCollections$ListN.get`. Root cause: source's fragile lookup-by-`toString()`-string-match idiom for `avocado_pit` (`ModItems.ITEMS.getEntries().stream().filter(v -> v.get().toString().equals("avocado_pit")).toList().get(0)`) found zero matches at runtime, because `avocado_pit` is registered as a real **block** (`ModBlocks.AVOCADO_PIT`, confirmed via javap - it has its own blockstate/model/loot table) in the resolved v0.17.8 jar, not a bare item in `ModItems.ITEMS`. Fixed by replacing the fragile stream lookup with a direct `ModBlocks.AVOCADO_PIT.get()` field reference. **This is exactly the kind of bug that only shows up with a live boot** - it compiled fine (the stream/lambda chain is valid Java regardless of what's actually in the collection at runtime).

## Runtime-only dependency gotchas (found by `runData`/`runServer`, not `compileJava`)

Each of these compiled fine but crashed the actual game/datagen boot with a missing-class or missing-mod error, because a transitive hard-dependency of one of our compat mods wasn't itself declared:

1. **Miner's Delight requires "lodestone" 1.7.0+** (a Lodestar-team rendering library) - added `maven.modrinth:lodestonelib:1.8.2` as its own runtimeOnly dependency.
2. **Farmer's Respite (unofficial port) requires JEI 19.27.0+** - our task-1-chosen `jei_version=19.24.0.317` was too old for this specific addon; bumped to `19.27.0.336` project-wide.
3. **Argentina's Delight Reborn requires "Player Animator"** (`dev.kosmx.playerAnim`) - `NoClassDefFoundError` on `IAnimation` at mod-construction time. Added `maven.modrinth:playeranimator:2.0.4+1.21.1-forge` (yes, "-forge" in the version string despite being a genuine dual Forge/NeoForge build per Modrinth's own loader tag - verified, not a mistake).
4. **`ModCreateRecipeProvider` (task 7) needs Create+Flywheel actually on the runtime classpath, not just compileOnly** - datagen unconditionally instantiates the provider class (no `isModLoaded` guard makes sense for datagen), so `runData` `NoClassDefFoundError`'d on `CrushingRecipeGen`. Added matching `runtimeOnly` lines for both `create-...:slim` and `flywheel-neoforge-...` (previously compileOnly-only, matching source's original Forge-1.20.1-era pattern which never needed this because source only ever *compiled* against Create, never *ran* with it in this exact way).
5. **Create itself requires Ponder 1.0.82+** - added `net.createmod.ponder:ponder-neoforge:1.0.82+mc1.21.1` (repo `maven.createmod.net`, same as Create/Flywheel).
6. **Create/Ponder require Registrate** - `NoClassDefFoundError` on `com.tterrag.registrate.AbstractRegistrate`. Registrate is NOT hosted on `maven.createmod.net` (despite Create's own official wiki listing that as the dependency-coordinate example) - the actual artifact for the `MC1.21-1.3.0+67` build lives at a **separate snapshot repo**, `https://maven.ithundxr.dev/snapshots/`. Added that repo scoped to `com.tterrag.registrate` only.

## Two mods deliberately excluded from the runtime classpath (compileOnly only) - genuine upstream bugs, not fixable here

1. **Carry On 2.2.6** - its only published "neoforge" 1.21.1 build (identical file on both Modrinth and CurseForge, filename `carryon-neoforge-1.21.1-2.2.6.13.jar`) is actually a **Forge-format jar**: legacy `META-INF/mods.toml` (not `neoforge.mods.toml`), manifest `Implementation-Title: Forge`, `MixinConfigs: carryon.mixins.json,carryon.forge.mixins.json` (a Forge-only manifest mechanism). NeoForge's loader hard-rejects it at boot: "is for Minecraft Forge or an older version of NeoForge, and cannot be loaded" - this crashes the entire dev environment if present on the runtime classpath. This looks like an upstream mod-author mislabeling bug (same file uploaded under both loader tags), not something fixable from our side. `com.github.fossil.compat.carryon.CarryOnCompat` + `com.github.fossil.mixin.PickupHandlerMixin` are fully ported and compile correctly (kept via `compileOnly`) - `PickupHandlerMixin`'s `require=0` means it silently no-ops with no target class present, confirmed via live `runClient` log ("`@Mixin target ... was not found`", not a crash). Revisit if/when Carry On ships a genuine NeoForge 1.21.1 build.
2. **Farmer's Respite (Unofficial Port) v3.0.0** - the only NeoForge 1.21.1 build that exists - crashes `RegisterEvent` dispatch with `IllegalStateException: Adding duplicate key 'ResourceKey[minecraft:menu / farmersrespite:kettle]' to registry`, a genuine internal double-registration bug in the port itself (confirmed unrelated to our compat code, which only touches food mappings). No newer version exists to try. `FarmerRespiteCompat.java` is fully ported and compiles (kept via `compileOnly`). Revisit if/when a fixed build appears.
