## IMPORTANT process gap discovered and resolved (retroactively affects tasks 3-8 too)

Investigating how task 9's generated worldgen JSON would actually ship, discovered: `build.gradle`'s `sourceSets.main.resources` includes `src/generated/resources` as a resource dir, but **nothing** (`jar`/`build`/`processResources`) has a `dependsOn` on `runData` — it's a fully manual step. Per [[fossils-phase7-task3-blockstate-item-providers]] and [[fossils-phase7-task4-tags-providers]], the established convention for tasks 3-8 was: run `runData`, verify output, then **delete `src/generated/`** afterward as "a build artifact, not a task deliverable." Confirmed by direct check: only 21 blockstate files / 30 item model files are actually committed in `src/main/resources` (matches the long-known "~197 blocks still need Phase 7 datagen models" gap from [[fossils-phase1-blocks-progress]]) — meaning most of tasks 3-8's generated content (block models, tags, loot, recipes, advancements) has never actually landed in the repo; it only existed transiently on disk during each task's own verification session, which is why e.g. "1290 recipes loaded" was true then but is NOT reproducible on a fresh checkout today.

For client assets this is a cosmetic gap (missing model = purple/black block). For task 9's worldgen registries it would be catastrophic if the same "verify then delete" pattern were followed — the mod would ship with zero biomes/structures/features, since Phase 6's currently-shipping hand-authored JSON was slated for deletion once "equivalent" Java-generated output existed only transiently in `src/generated/`.

**User's decision (2026-08-14, asked directly)**: commit generated JSON permanently. The corrected workflow going forward, for task 9 AND retroactively for tasks 3-8's leftover gap: `runData` → verify correctness → **move** (not delete) the generated files from `src/generated/resources/` into the matching path under `src/main/resources/` (replacing old hand-authored equivalents there) → `git add`/commit as normal resources → THEN delete `src/generated/`. Java bootstrap/provider code becomes the authored source; the emitted JSON becomes the checked-in deliverable, same as any other resource — no build-pipeline changes (no `dependsOn` wiring) needed.

**Follow-up not yet scheduled**: tasks 3-8's block models/tags/loot/recipes/advancements/food-values still need this same backfill (re-run `runData`, move output into `src/main/resources` for real this time) — flagged to the user as a separate, deferred item, not blocking task 9's own progress. Whoever picks this up next should treat it as its own checkpoint-worthy task, not silently fold it into task 9.
